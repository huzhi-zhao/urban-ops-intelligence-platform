# ADR 0008 — 排班表是计划而非执行记录：供给侧口径改为「排班顺位」

> **Status**: Accepted · **Date**: 2026-08-07
> **Supersedes**: [ADR 0007](0007-clearing-completion-time-source.md)

决策：`tix9-r5tc` **不是**清雪执行记录，是**排班计划表**。因此

1. `shift_end` **不得**再解析为摘要里的 "actual street-clearing completion times"；
2. BO-6 评分中的**「作业缺口」因子予以删除**——该指标恒为假；
3. 供给侧改由 **`shift_number` 排班顺位**承担，它度量的是**轮候位次**，
   不是完成时刻。

---

## 1. 背景：ADR 0007 的事实前提被实测推翻

ADR 0007 §2 写道：`shift_end` 的语义是「某个作业分区某个班次的**实际**起止时刻」，
并据此断言它是「市政记录的真实作业数据，不是估计值也不是代理指标」。

**2026-08-07 对全表 418 行做结构实测，这个断言不成立。** 复现查询见 §6。

| 实测结果 | 含义 |
|---|---|
| 19 个 `snow_ban_id`，每个**恰好 22 行 / 22 个 `plow_zone`**，一个不多一个不少 | 不是执行产生的记录，是排布出来的表 |
| 每个事件总窗口**固定 60 小时**（07:00→19:00+2d 或 19:00→07:00+2d） | 固定时长，与雪量无关 |
| 22 个分区分进 **5 个班次**，每班整 12 小时，依次排开 | 模板化排班 |
| **同一班次内所有分区的 `shift_start` / `shift_end` 完全相同** | 分区之间零方差 |

一张记录真实作业的表不会有这些性质。真实执行必然有延误、有超时、有分区间差异。
这张表**不含任何执行信息**：没有实际出车、没有完成确认、没有延误记录。

它记录的是「这次禁令期间，各分区被安排在第几个 12 小时班次」——**一份计划**。

---

## 2. 决策

### 2.1 摘要口径

`actual street-clearing completion times` 这一表述**在现有数据上无所指**，
必须改。改动路径已由
[business-objectives.md](../requirements/business-objectives.md) §0.2 预留：
尚未正式投稿，措辞经导师同意后可调整。ADR 0007 §3.3 曾以「没有必要」否决过
修改摘要——**该否决理由随其事实前提一并失效**。

替代表述指向真实存在的量：

- ✅ *the order in which zones are scheduled during a city-wide plow operation*
- ✅ *how long a zone waits before its shift begins*
- ❌ *actual street-clearing completion times*（无对应数据）
- ❌ *per-zone completion time / clearing duration*（同班次分区完全相同，无信息量）

### 2.2 供给侧的新口径：排班顺位

| | 采用 |
|---|---|
| 字段 | `tix9-r5tc.shift_number`（配合 `snow_ban_id` 定位事件） |
| 语义 | 某分区在某次全市犁雪中被安排在**第几个 12 小时班次** |
| 粒度 | 分区 × 事件 |
| 覆盖【实测】 | 19 事件 × 22 分区 = 418 行，**零缺失** |
| 派生指标 | 分区平均顺位 · 顺位离散度 · 轮候时长（顺位 × 12 h） |

实测的分区平均顺位（19 次事件）：

| 分区 | 平均顺位 | 分区 | 平均顺位 |
|---|---|---|---|
| **C** | **3.47** | … | … |
| A | 3.32 | P / G | 1.79 |
| B | 3.21 | **S** | **1.26** |

**极差 2.2 个班次 ≈ 26 小时，十年十九次，二十二个分区无一缺席。**

### 2.3 删除「作业缺口」因子

原定义：降雪事件发生但该分区无排班覆盖 → 判为未出动，占 BO-6 评分 0.30 权重。

**它恒为假。** 19 次事件全部 22/22 全覆盖，从来没有任何分区被漏掉。

更严重的是它是**系统性假阳性**：这张表只记录会发停车禁令的**全市住宅区集中犁雪**
（10 年 19 次，每冬不到 2 次）。主干道日常维护、撒砂、局部清理**根本不在表内**。
因此「无排班记录」推不出「没干活」——按字面定义计算，只会把「这类作业不进这张表」
误读成「这里没人来过」。

0.30 权重转给排班顺位因子。

---

## 3. 无排班分区必须显式排除

边界表 `39ur-higg` 有 **25 个 `plow_zone` 取值**，排班表只有 **22 个**（A–V）。
差集在排班表中**没有任何记录**：

| 取值 | 多边形数 | 地址数【实测】 |
|---|---|---|
| `B/D` | 1 | 11,150 |
| `X` | 8 | 2,590 |
| `Downtown` | 1 | 574 |
| 合计 | 10 | **14,314（占已归属地址 6.0%）** |

**这三个取值不得进入任何顺位排名。** 「无排班记录」不是「排在最后」——
把它读成后者，正是 §2.3 删掉作业缺口因子的那个错误再犯一次。
`B/D` 的一万一千个地址尤其需要先弄清它是边界表的历史遗留标签、还是真有一块区域
不进全市犁雪排班。

## 4. 后果

### 4.1 叙事从「运营决策」转向「回溯问责」

三个原定问题按新口径重估：

| 问题 | 状态 | 原因 |
|---|---|---|
| 哪里最惨 | ⚠️ 降级 | 官方有 GPS、作业记录、路况巡查；我们只有投诉这一个代理变量 |
| 为什么惨 | ✅ 改口径后成立且更强 | 「作业缺口」是假阳性；「排班顺位」不是 |
| 下次先去哪 | ⚠️ 限定范围 | 派车优先级是**政策**规定（P1 主干道→P2→P3 住宅区，有法定时限），不接受数据挑战。项目只提供「同优先级内部谁先谁后」这层边际信息 |

项目的价值位置随之明确：**不是在运营决策上比官方更准，而是在官方结构性不会去做的
位置上，做一份公开可复核的冬季运营回溯基线。** 说服力来自可复核，不来自精确。

### 4.2 表述纪律：顺位差异 ≠ 不公平

顺位差异可能有完全正当的理由——路网长度、人口密度、机械调度路线、地理位置。
**本 ADR 不授权任何「不公平」结论。** 唯一可作的陈述是：

> 这个差异是**稳定且系统性的，十年没变**。它可能完全合理——
> 但目前没有任何公开文件解释这个顺序是怎么定的。

即：把一件此前无法讨论的事变成可讨论的，球踢给市政。

### 4.3 交叉验证已完成：轮候集中在地址最多的分区

用 `g3p4-h83y` 的 237,867 条地址点做点在多边形内归属，再与顺位对齐
（脚本 `scripts/analysis/zone_schedule_rank.py`，实测 2026-08-07）：

- **空间命中率 237,858 / 237,867 = 100.0%**（9 条无坐标）
- **Pearson r(平均顺位, 地址数) = +0.491**
- 排最后三位的 C / A / B 合计占全市地址 **25.2%**；排第一的 S 区仅 **2.8%**

结论落在「更尖锐」的一侧：**等待最久的分区，恰好也是等待人数最多的分区。**
该结论受 §4.2 的表述纪律约束，且须同时说明归一化分母是当期快照
（见 BO-6「归一化分母的局限」）。

### 4.4 ADR 0007 中继续有效的部分

被推翻的只有「`shift_end` = 完成时间」这一条及其直接推论（§2、§2.1、§3.3）。
下列结论**不受影响，继续有效**：

- §3.1 `g3p4-h83y` 地址级状态在本次交付窗口内数据量为零 → BO-7 不进证据链
- §3.2 311 的 `closed_date` 度量的是需求侧响应，不能充当供给侧数据源
- §4.1 空间对齐是承重连接 → **BO-4 的地位不降反升**：顺位分析同样只有分区粒度，
  报告单元仍是 neighbourhood / ward，交叉映射表依旧是单点依赖
- §4.3 映射表可用带坐标的冬季工单做经验加权，不必另找 neighbourhood 边界
- §4.4 分析单元锁定「降雪事件 × 分区」，事件由气象切分而非由市政响应切分

### 4.5 §4.2 的降级方案已确定不会触发

ADR 0007 §4.2 把「`39ur-higg` 未实测」列为最大风险，降级方案是放弃分区维度。
本篇的 §4.3 交叉验证顺带关闭了它：**82 个多边形对全市地址完整覆盖，命中率 100%**。
`location-aware` 的表述无需减弱。

## 5. 被否决的方案

### 5.1 保留 `shift_end` 作为完成时间，只在脚注里说明它是计划值

**否决理由：那是把一个已知为假的陈述留在标题里，用脚注免责。**
同班次分区的 `shift_end` 完全相同，"per-zone completion time" 这个量的方差为零——
不是不精确，是不存在。演讲现场只要有一个人查一下这张表就会发现。

### 5.2 保留作业缺口因子，改为在 2015-12 之后才计算

**否决理由：时间窗口不是问题所在。** 缺口因子在 2015-12 之后同样恒为 0
（19/19 全覆盖）。原 BO-6 §「有效分析窗口」处理的是「缺失不等于缺口」，
而本篇发现的是「有记录也不等于有覆盖信息」——两个不同的缺陷，前者的修法治不了后者。

### 5.3 改用 `mfzv-893p` 禁令表定义供给侧

**否决理由：样本更少，且度量的是决策不是执行。** 49 条禁令、19 次作业。
禁令表能支撑的是 BO-3 的「决策滞后」指标，已在用，不需要它再承担供给侧主口径。

### 5.4 等 BO-7 攒够快照再讲供给侧

**否决理由：交付窗口内不可能。** 采集 2026-08-02 上线，首批有分析意义的记录要等
当年 11 月之后的降雪季，而会期是 2026-09-19。这与 ADR 0007 §3.1 的判断一致。
BO-7 的位置仍是贡献声明，不是本次证据链。

## 6. 复现查询

```bash
# 19 个事件的整齐度：每个都是 22 行 / 22 分区 / 60 小时窗口
curl -s "https://data.winnipeg.ca/resource/tix9-r5tc.json?\$select=snow_ban_id,count(*)%20as%20n,min(shift_start)%20as%20first_start,max(shift_end)%20as%20last_end,count(distinct%20plow_zone)%20as%20zones&\$group=snow_ban_id&\$order=first_start"

# 单个事件内的班次结构：22 分区 → 5 个班次 × 12 小时
curl -s "https://data.winnipeg.ca/resource/tix9-r5tc.json?snow_ban_id=32671933&\$select=plow_zone,shift_number,shift_start,shift_end&\$order=shift_start,plow_zone"

# 各分区平均排班顺位（§2.2 的表）
curl -s "https://data.winnipeg.ca/resource/tix9-r5tc.json?\$select=plow_zone,avg(shift_number)%20as%20avg_shift,min(shift_number)%20as%20min_s,max(shift_number)%20as%20max_s,count(*)%20as%20events&\$group=plow_zone&\$order=avg_shift%20desc"
```
