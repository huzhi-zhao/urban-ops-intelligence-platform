## 1. 背景：原判据依赖一个仓库里没有证据的前提

H2 原来的判据是一句话：**陌生团队照 `guide/` 能否独立跑起来并接手运维。**
它把工作内容完全确定下来（一键拉起全栈、查询层、契约冻结、可观测性、runbook、
CI/CD、数据字典），这正是它当时的优点。

但这句话有一个未写出来的前提：**存在想接手的人。** 仓库里没有任何证据支持它——
摘要至今未被会方接受、也尚未正式投稿（business-objectives.md §0.2），
没有任何外部使用者、下游消费者或接手方的记录。判据依赖的前提不成立时，
继续按它排期，等于给一个**没有读者的服务**做运维面。

同时，这套服务的分析内核有几条**已经量过、写在台账里的**上界，它们不会因为
运维面做得更完整而移动：

| 上界 | 数 | 出处 |
|---|---|---|
| 311 工单没有坐标 | 79% | business-objectives.md §2.1 |
| 清雪状态上游覆盖式更新、不留历史，漏采即永久缺失 | —— | BO-7 · `docs/guide/snapshot-collection.md` |
| 「模型优于基线」不是可辩护的公开结论 | —— | BO-8 §0.2.2 · L3 launch §8 ③ |
| M1 的训练面板 | 2,178 格 | L3 launch §3.3 |
| 留出季里的降雪事件 | 7 个 | L3 launch §3.3 |
| 全市犁雪作业总数（十年） | 19 次 | 台账 C2-7 |

🔴 **这些是样本量的上界，不是实现质量的上界。** 换更强的模型、更完整的手册、
更多的看板，都不会把 19 次作业变多。任何以「再补一层外围工作」为形式的计划，
都绕不过它们。

## 2. 决策

**H2 的判据改为：把已经认证过的 Gold 收成一个能被读者验证的诚实回答，
然后停在那里。**

### 2.1 保留三样，其余取消

| | 项 | 处置 | 理由 |
|---|---|---|---|
| ✅ | Trino 查询层（Hive Metastore + Trino） | **保留，已在** | 已部署且是所有取数的入口，成本已付 |
| ✅ | DQ 审计与 Gold 认证（ADR 0012 三批） | **保留，已在** | 页面上每个数都带认证状态；这是「诚实」唯一可执行的形式 |
| ✅ | 数据字典 | **保留为唯一新增的运维面工作** | 语义层是读者和任何后续消费者都需要的，且它服务的是数据本身不是运维 |
| 🚫 | 一键拉起全栈 | 取消 | 服务的是「接手方跑起来」，该前提不成立 |
| 🚫 | Grafana 看板（栈里唯一未部署组件） | 取消 | 同上；运行状态三张图（台账 §8）随之不做 |
| 🚫 | runbook / 失败路径手册的完整度 | 取消 | 现有 `docs/dev/operations-gotchas.md` 已覆盖真实踩过的坑，**够用即止** |
| 🚫 | Superset 报表面 | 取消 | Superset 已部署，继续做报表是给没有读者的服务加读者界面 |
| 🚫 | 「集成测试在真 MinIO 上全绿」作为 H2 判据 | 降级为待办 | 生产已用真实流量验证过；它是套件层面的复核，不再是一条判据 |

### 2.2 新的完成判据

H2 完成 = 下面三条同时成立：

1. **读者能对着一个页面，自己选分区，拿到两个问题的答案**：
   「为什么我这里扫得慢」与「下次是不是轮到我优先」。
2. **这两个答案都不越过证据**：第一个是查表（历次排班顺位分布），
   第二个是一条规则的回测命中率（「照抄上次」），
   **两个都不是模型输出**，页面上也不许这么写。
3. **页面上的每条保留都出现在页面上**，不是出现在文档里：
   计划不是记录 · 粒度是分区不是街道 · 只覆盖住宅街道 · 三个分区无排班
   （占地址数 6.02%）· 顺位会漂移 · 靠后不等于不公平。

### 2.3 落地形式

- `sql/presentation/fig_bo2_06_zone_rank_profile.sql` —— 逐分区顺位档案，
  驱动表是 **25 个分区**而不是顺位面板的 22 个。
- `sql/presentation/fig_bo2_07_rank_persistence.sql` —— (分区, 上次班次, 下次班次)
  的转移计数，396 对。
- `carrier: lookup` —— 第四个载体值。执行与冻结路径与其余图**完全相同**，
  只决定由 `scripts/presentation/zone_lookup.py` 而不是 `render_html.py` 消费。
- 页面与入口：`make portfolio` 把两份 payload 折成 `dashboard/public/data/lookup.json`，
  portfolio 站点的 `#/zone` 页读它，导航里叫 **Your zone**。
  > 📝 **更正（2026-09-14 落地时）**：本条原写「`make zone-lookup` 产出
  > `zone-lookup.html` 与 `index.html`」。落地时 `dashboard/` 已是一套 React
  > 站点，再出一个静态页等于让同样两个问题有两个入口、两份文案要同步，
  > 于是页面并入 `#/zone`，`zone_lookup.py` 只留下经过单测的折叠逻辑。
  > **判据不变**：读者选一个分区，拿到两个不超出证据的答案。

🔴 **比率一律在页面上加总后算一次，SQL 只出计数。** 按分区平均命中率会让
18 次转移的分区与全市等权——与 `.claude/rules/gold-sql.md` R3 同一条理由。

🔴 **「照抄上次」的命中率必须与一个对照一起出现。** 89.5% 的格落在 1–3 班
（台账 C2-8），所以一个固定猜测本来就能拿到很高的 ±1 命中率。页面因此同时给出
「每次都猜第 N 班」的命中率。**这不是「规则优于基线」的结论**，18 次转移也不足以
下这种结论；它的作用是让读者知道该拿什么和 83% 之类的数比。

## 3. 与 BO §0.1 的关系：收窄，不是推翻

§0.1 明确不做「除雪状态查询地图、分区查询 app、实时进度看板」，理由是与官方
**Know Your Zone** app 及官方近实时地图重复。这条继续成立，但它划的线是
**当前状态 vs 回溯分析**，不是「按分区 vs 按全市」。

本页面落在回溯那一侧：它只讲**已完成的 19 次作业**里这个分区排第几，
以及一条规则历次的命中率。它**不知道今天这一场发生了什么**，也不回答
「我家这条街清了没」。判据是一句话：**它能不能回答「现在」？**
能，就是官方那边的活。

🔴 因此页面**不得使用官方工具的名字**，也不得让读者以为它知道当前状态。
页面标题是「Where your zone sits in the order」，并在保留里直接把读者指回
官方工具。单测 `test_the_page_does_not_present_itself_as_the_city_status_tool`
钉死这一条——这条线只有在措辞上守住才是真的。

## 4. 被否决的方案

1. **继续按原判据做完运维面。** 否决理由见 §1：判据的前提在仓库里没有证据，
   且几条上界不因运维面而移动。
2. **在 Gold 上换一个更强的模型来回答「下次是不是轮到我优先」。**
   否决：目标粒度是降雪事件 × 分区，十年只有 19 次作业、2,178 格面板、
   留出季 7 个事件。换模型撞的是同一面数据墙，而且会把一个**可以诚实回答**的
   问题重新包装成一个不可辩护的结论。顺位在历史频率上是可以直接查表的
   （台账 C2-1/C2-3），这比任何模型都更准也更好讲。
3. **把页面做成地址输入 → 自动定位分区。** 否决：
   `silver_service_request` 的空间归属能力在（`zone_assignment`，命中率
   99.9%），但地址级 geocoding 是一条新的上游依赖，且**官方 app 已经做了这件事**，
   §0.1 的线正好落在这里。读者知道自己的分区，或者去官方工具查——
   页面从分区开始。
4. **把「先做哪个 AI 方向」一起在本篇定下来。** 否决：H1（2026-09-19）之前
   不开新坑，而方向选择需要单独一轮收敛。本篇只取消原 H2 的清单，
   **不指定替代方向**。

  上的产出（口径更正、分页事故复盘、三态认证、禁语清单）是否构成本项目最硬的
  部分，属于对外表述的范围，由 `business-objectives.md` §0.2 那份合同管，不在这里。
