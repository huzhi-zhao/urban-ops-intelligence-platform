# 快照采集上线

> **Status**: Draft · **Date**: 2026-08-02

选型层面的取舍已在 [ADR 0006](../adr/0006-storage-compute-query-stack.md) 定案
（为什么是 MinIO、为什么 gzip、为什么这个任务不进 Airflow）。本篇只定
**这一次上线分几批、每批的边界在哪、怎么算上完**。运维手册在
[guide/snapshot-collection.md](../../guide/snapshot-collection.md)，本篇不重复命令。

---

## 1. 问题

BO-7 的上游 `g3p4-h83y` 是覆盖式快照，无任何时间字段，不保留历史。
**采集推迟一天，就永久少一天历史**，且该缺口事后无法由任何手段补上。这是全项目
唯一每天都在损失价值的事项；其余全部是存量债务，债务不增长。

代码侧的前置条件已经具备：`snapshot` 分区策略、流式写入、小样本闸门、
失败通知与死人开关、CLI 入口都已实现并有单测覆盖。

**唯一的真实未知数是环境**：所有对象存储代码只跑过 mock 单测，MinIO 从未被真实
写入验证过。因此本次上线的性质不是"开发"，而是"把一条已经写好的链路在一台从未
验证过的机器上跑通，并让它在无人值守下持续跑下去"。

---

## 2. 约束

**冻结的在盘契约。** 路径布局
`bronze/raw/{sid}/{ds}/ingest_date=YYYY-MM-DD/data.ndjson.gz` + `manifest.json`
及 manifest 字段语义（`file_size_bytes` / `sha256_checksum` 描述**未压缩**载荷，
`compression` / `stored_bytes` 描述存储对象）是**已冻结的契约**。实现可以重写，
已落盘的数据不能重写——快照历史不可重新生成，所以第一天落下去的形状就是最终形状。

**`.gz` 扩展名是正确性条件而非命名习惯。** Spark 的 `s3a://` 读取器按扩展名选择
解压编解码器并忽略 HTTP 头，扩展名错误会产出乱码行且**不抛异常**
（[ADR 0006 §4.1](../adr/0006-storage-compute-query-stack.md)）。

**补救窗口是当天，不是零。** 漏一天不可补，但上游随时可重新拉取当前状态——当天
之内发现失败并重跑，这一天就没丢。这个事实决定了可靠性设计的方向：目标是把
**发现故障的时间压到小时级**，而不是把单次成功率推向 100%。后者做不到，前者能做到。

**分区标签由机器本地日期决定。** 采集器默认以 `date.today()` 命名分区，systemd
定时器同样按本地时区触发。机器时区若与温尼伯不一致，分区标签会整体错位。

**存储节点是长期无人值守的小机器。** 可动部件越少越好：它只需要 HTTP 客户端、
对象存储客户端和配置解析，不需要计算栈。

**显式接受的风险**：不做备份与 DR（[platform-architecture.md](../platform-architecture.md)），
本次不做冗余采集——理由见第 4 节。

## 3. 方案

四批，按"是否在流血"排序，不按工作量排序。前三批必须同日完成，第四批与前三批
同批交付，否则等于没上线。

### 批 0 · 保险副本

在触碰 MinIO 之前，先把当天的全量数据落到存储节点本地磁盘。它不是 Bronze
（非 NDJSON、无 manifest），只是一份保险：若后续批次卡住，当天的数据仍在，可按
冻结契约事后补写；一旦上游过夜覆盖，则永久丢失。

批 0 的存在本身就是对"MinIO 未验证"这一风险的对冲——**先保住数据，再谈跑通链路**。

### 批 1 · 存储节点环境

三件事：非特权用户 + 只读代码 + 最小依赖 + 受限凭证。

- **代码分发用只读 deploy key（SSH）**，不用带令牌的 HTTPS URL。带令牌的 URL
  会把一份可写凭证复制到无人值守的机器上，且无法单独吊销。
- **依赖只装实际 import 的那几个包**（HTTP、对象存储、配置校验），不执行整仓
  依赖同步。整仓主依赖含 Spark，那是这台机器上永远不会被 import 的数百 MB
  可动部件，只会增加操作系统升级弄坏运行环境的概率。
- **对象存储凭证单独一把**，策略限定在该源的前缀上，只给写入与分段上传，
  **不给删除**。18.5 MB 的对象会走分段上传，权限须覆盖分段的四个动作。
  攒了半个冬季的历史，不应由一把无人值守的密钥承担被误删的风险。
- **配置文件不进仓库**，属主与运行用户分离（运行用户可读、不可改自己的凭证）。

### 批 2 · 首日落盘

先 dry-run 核对上游记录数量级，再真实采集，再回读确认对象与 manifest 成对存在、
压缩比合理。这一刻起出血停止，后续全部是加固。

同一次全量拉取顺带为 BO-6 提供"分区地址数"这个归一化分母
（[business-objectives.md](../requirements/business-objectives.md) BO-6），不需另跑。

### 批 3 · 自动化与告警

- **定时器写明时区**，不依赖机器的默认时区；配置漏采后的补跑（关机错过的窗口在
  开机后补一次）。
- **同一天内的失败自动重试**：定时器仍是每天一次，重试挂在"失败"这个条件上，
  而不是无条件多跑几次。理由见第 4 节。
- **失败通知**（进程还活着时自报）与**死人开关**（外部服务在没等到打卡时反向告警）
  两条都要配。后者覆盖的是"进程根本没跑"——那种情况下没有任何活着的进程能发通知，
  而它恰恰是真正损失历史的那一类。
- **死人开关的宽限期必须短到当天还能补救**。这是本次上线最高杠杆的一个参数：它
  决定了故障发生后你还剩几个小时。宽限期设得比一天还长，等于把可恢复的故障变成
  不可恢复的。
- **告警必须能推到手机**。邮件在睡觉时等于没有。

### 后续加固（不阻塞本次上线）

- 采集器增加"当日分区已存在则跳过"的开关，使自动重试与人工重跑都不会用当日较晚
  时刻的状态覆盖较早的成功采集；之后才谈得上挂第二个定时器。
- 计算节点上已有的 Bronze 审计任务接入快照的**只读**核对，作为独立失效域的第二层网。
  只核对不补采——快照"补"只会把今天的数据写进昨天的分区，那是伪造历史。
- 积累一周基线后抬高小样本闸门。当前默认值相对真实行数低两个数量级，一次残缺的
  上游响应足以通过闸门并覆盖当日分区。

## 4. 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 作为 Airflow DAG 运行 | 不可重放的采集不应依赖可重建组件的可用性。已在 [ADR 0006 §2.2](../adr/0006-storage-compute-query-stack.md) 定案，本篇不重开 |
| 等自建栈迁移全部完成再上线 | 迁移剩余项（Terraform 退役、手册同步、Spark 侧改造）不阻塞任何采集。为"迁干净"推迟上线，代价是不可再生的历史 |
| 一天无条件跑三次以提高成功率 | 不同时刻拍到的是不同的清雪状态。BO-7 要的是纵向**可比**的序列，采集时刻应当固定；无条件的第二次运行会用晚间状态覆盖清晨状态，污染序列语义。正确形态是只在失败时重试 |
| 用整仓依赖同步部署运行环境 | 会在存储节点装入永不 import 的计算栈。见批 1 |
| 用带令牌的 HTTPS URL 克隆代码 | 等于把一份可写凭证长期放在无人值守的机器上 |
| 本次就做第二台机器的冗余采集 | 它只覆盖"采集进程失效"，覆盖不了"存储服务失效"——两台都写同一个对象存储。在"小时级发现故障"尚未建立之前，冗余的边际收益低一个数量级。等历史积累出分量后再评估 |
| 用 cron 而非 systemd timer | cron 以近乎空的环境运行，是"手动能跑、定时不能跑"的最常见原因；且不记录退出状态、不补跑错过的窗口 |

## 5. 验收判据

按顺序，每条不过不进入下一条。

1. **对象存储真实往返通过**：集成测试全部真跑而非 skip（skip 即环境变量没被读到）。
   它覆盖 upload → download → 解压 → 比对，正是 mock 测不出的那个失效模式。
2. **dry-run 的记录数与调研实测同量级**（[winnipeg-data-sources.md](../requirements/winnipeg-data-sources.md) §4.3）。
   量级不符则停止，不得继续。
3. **首日分区存在且成对**：`ingest_date=<当日>/` 下同时有 `data.ndjson.gz` 与
   `manifest.json`，压缩后体积与容量基线相符（[data-volume-baseline.md](../data-volume-baseline.md) 的实测压缩比）。
4. **在定时器的空环境下跑通**：手动触发一次服务单元成功，而不是在交互 shell 里成功。
5. **下一次触发时间落在预期的当地时刻**，而非机器默认时区推算出的另一个时刻。
6. **死人开关收到打卡**，且人为跳过一次采集后能在宽限期内产生告警。第 6 条是唯一
   直接验证"漏采会被发现"的判据，不能省略。

## 6. 开放项

| 事项 | 建议 | 什么时候必须定下来 |
|---|---|---|
| 小样本闸门的取值 | 积累一周基线后抬到真实行数的量级附近，留足上游正常波动的余量 | 上线后一周内 |
| "当日已存在则跳过"的开关 | 单独一个改动，含单测；在它落地前，重试只挂在失败条件上 | 挂第二个定时器之前 |
| 冗余采集是否要做 | 先把"小时级发现"建立起来再评估；若做，须解决"存储服务失效时落本地、事后补传"，否则两台机器共用一个失效域 | 积累一个完整降雪季之前 |
| 手册与本篇的偏差 | 现行手册的依赖安装与定时器单元与本篇方案不一致，应在本次上线时一并修订 | 批 3 完成时 |
| 上线记录 | 实际过程与本篇的偏差记入 [launch/](../launch/README.md)，不回写本篇 | 上线当日 |
