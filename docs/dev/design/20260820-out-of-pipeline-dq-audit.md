## 1. 为什么单开一篇：L3 里没有这件事

先回答「L3 是不是已经包含它」。**不包含。**
L3-c（[scoring-chain-and-m1 §3](20260817-scoring-chain-and-m1.md)）交付的是：

> 每张表记录行数 · 各列空值率 · 分区完整性 · 构建耗时 …… L1/L2 跑完的当时
> 就分别记进各自的 launch，L3 只做汇总 + 补测试四件套。

这是**一次性的基线快照**，性质上属于「管道内 + 上线门禁」：它在构建的那一刻
测一次，写进 launch 文档，没有调度、没有第二次、没有趋势、没有跨层对账、
没有对下游的打标。它是本篇的**输入**（阈值的唯一依据），不是本篇。

真正属于「管道外」的碎片今天散在三个地方，谁都不拥有它：

| 碎片 | 现在在哪 | 状态 |
|---|---|---|
| Bronze 内容正确性（校验 B 分片内唯一 / 校验 C 上游行数对账） | 复盘附录 + L2 的 **O8** | 探针已实现，未进任何调度 |
| Silver 分区完整性 | L2 **O7** —— 挂在 Gold 构建器的前置检查里 | 只在手动构建 Gold 时才跑 |
| 逐列空值率、行数基线 | L1/L2 launch 的一次性实测 + L3-c 汇总 | 静态数字，无人复测 |

**本篇把这三块合成一件事，并从 L3 拎走一部分。**

### 1.1 与 L3 的边界（拎走 / 留下）

| | 归属 | 理由 |
|---|---|---|
| DQ **基线**（一次性测量 + 写进 launch） | **留在 L3-c** | 它是上线门禁的一部分，跟着那次构建走 |
| 测试四件套（`unique` / `not_null` / `relationships` / `accepted_values`） | **留在 L3-c** | 是结构性断言，属于管道内（见 §2 分类①） |
| **定时复测、趋势、跨层对账、计分卡、certified/suspect 打标** | **本篇** | 需要「多次运行之间比较」，L3 只跑一次 |
| Bronze 校验 B/C 进 `dag_audit_bronze`（L2 **O8**） | **本篇接管** | O8 那个 PR 就是本篇的第一批实现 |

🔴 **L2 的 O8 不因此推迟。** 它已经排了独立 PR，照做；本篇只是给它一个
上位的框架，让第二批第三批不必再各自发明结构。

## 2. 管道内 vs 管道外

平台已有的所有质量手段都在管道内。两类的差别不是检查项，是**权力**：

| | 管道内（in-pipeline） | 管道外（out-of-pipeline） |
|---|---|---|
| 谁跑 | ETL job / Gold 构建器自身 | 独立 DAG，自己的 cron |
| 何时 | 写盘前 | 数据**已经落盘之后** |
| 失败后果 | **抛异常，数据不落盘** | 只报告与打标，**不阻断** |
| 能看见 | 本次窗口 / 本次构建 | 跨批次、跨层、跨时间 |
| 已有实现 | `assert_unique` · `enforce_schema` · `spatial_hit_rate` · Gold 的精确行数门禁（R4） | **无** |
| 典型漏网 | 慢性漂移、静默停更、跨表不一致 | 无法阻止坏数据进 Gold |

> 一句话：管道内回答「这一批能不能写」，管道外回答「已经写下去的这一堆，
> 今天还成立吗」。**分页无序那次故障两边都该抓、两边都没抓**——管道内的
> `assert_unique` 只覆盖被跑到的窗口，管道外根本不存在。

### 2.1 本篇不动管道内的任何一条

现有的管道内断言**全部保留原样**，一条都不迁出来。理由：它们的价值恰恰
在于「不落盘」，搬到管道外就退化成事后通知。本篇是**增加一层**，不是重构。

## 3. 六个维度（对齐流程图）

四个大类，落到六个维度的计分卡。**每一条都必须能回答「谁修、修什么」**，
不能回答的不进清单。

### 3.1 结构性 DQ —— 查「形状对不对」

| 检查 | 说明 |
|---|---|
| Schema / Type | 落盘的 Parquet 列与 `sql/ddl/` + `contracts/` 三方一致 |
| NULL | 契约声明 `nullable: false` 的列真的没有空值 |
| Duplicate | PK 重复行。**PK 从契约派生，不写在 DAG 里**（复盘附录第 1 条） |
| Required Fields | 关键字段是否整列缺失 |

⚠️ 与管道内重叠是**有意的**：管道内只看被跑到的窗口，管道外覆盖全部历史。
2019 之前那 9 个窗口全绿并不能说明那些天干净。

### 3.2 统计性 DQ —— 查「量级对不对」

| 检查 | 说明 |
|---|---|
| Row Count | 行数与历史区间对比 |
| Null Rate | 空值率突变（基线来自 L2 阶段 E1 的逐列实测，**全空列 0，六列非零空值已有语义解释**） |
| Distribution | 均值 / 分位数漂移 |
| Freshness | 最新分区日期是否停更 |

🔴 **Freshness 的阈值必须容忍「最近一两天天生偏薄」**（O17 定案：上游 311
发布滞后约一天，08-18 当天只有 8 行，同一天再问是 3,006）。
把稳态当缺口就是造一个天天响然后被静音的告警。

🔴 **空间命中率一律走 `zone_assignment.spatial_hit_rate()`，分母是 `has_geo` 子集。**
上游 79% 无坐标，全表口径的阈值永远报警。这条已经是 L1 的定案，审计层不得另算。

### 3.3 业务性 DQ —— 查「意思对不对」

| 检查 | 说明 |
|---|---|
| KPI Checks | 指标口径与 BO 定义一致 |
| Range / Logic | 值域、时序先后（`closed_ts_utc >= open_ts_utc`） |
| Plausibility | 数字像不像真的 |

这一维是**最容易写成主观题**的一维，因此要求：每条业务断言必须指向一个
BO 编号或一个 launch 里记过的实测数字，否则不写。已有的可用锚点举例：
`dim_plow_zone` 25/8/3 · `fact_parking_ban` 49（19 匹配 / 30 NULL，
**语义不是缺数据**）· F1 的非零格 **下界 ≥ 880**（908 是实测，916 已失效）。

🔴 **注意 F1 那条为什么是下界**：Open-Meteo 会回修历史存档，`segment_events`
重新切一遍，非零格随之上下动 1–2 格。管道外审计**天天**跑，把这种正常漂移
写成等值断言就是天天告警。**哪些等值、哪些下界，要逐条决定，不能一刀切。**

### 3.4 跨层对账（本流程独有）

三层都已落盘才比得了，这是管道内做不到的一件事：

- **Bronze → Silver**：原始行数 −（去重数 + 隔离数）是否守恒。
  已有锚点：全量首次落地时 Bronze = Silver = **12,474,313**，拒绝行 0。
  🔴 **分母不是 18.4 M**（那是上游整表；Bronze 采集范围有意不是全历史）。
- **Silver → Gold**：明细求和 vs 聚合值是否一致（roll-up）。
  已有锚点：Gold 建表当时 Silver 行数 12,477,414 与建 Gold 时逐行相同。
- **Bronze ← 上游**：即复盘附录的**校验 C**，唯一能发现丢行的一层。
  容差**只给最近 N 天**（迟到工单），历史天不给。

> 🔴 **重复与丢失在行数上相互抵消**（复盘 §结论①），所以扫描（校验 B）与
> 对账（校验 C）**缺一不可**，不能因为「行数对得上」就省掉一层。

### 3.5 计分卡与闭环

- 按六维汇总通过率与趋势，落 **`dq_audit_log`** 表（§5）。
- 所有 `error` 级检查通过 → Gold 打标 `certified`，下游放心消费；
  否则 → 告警 + 人工复核，Gold 标 `suspect`，看板挂「数据待核实」。
- FAIL 之后走**根因分析 & 规则迭代**：源系统坏了？转换逻辑错了？还是规则过严？
  → 修复回填走 CLI（**审计不改数据**），更新规则后重跑审计。

🔴 **规则过严是三个候选里最可能的一个**，且是唯一一个「修 Gold 修不好」的。
上面 F1 的例子就是：门禁写 916、实测 908，错的是门禁不是表。
**迭代规则也是闭环的合法出口**，不是失败。

## 4. 明确不做

| 不做 | 理由 |
|---|---|
| **阻断**。审计不 fail 管道、不删数据、不改 Bronze | Bronze 不可覆写（AGENTS.md）。产出是重拉名单，重拉走 CLI |
| 在审计里去重 | 同上；去重会掩盖上游变更这个信号 |
| 把管道内断言迁出来 | §2.1。它们的价值在于不落盘 |
| 每天全量扫 4,878 个分片 | 日常走滚动窗口（14 天 / 3 个月，与现有一致），全量是**手动入口** |
| 引入 dbt / Soda Core / Great Expectations 作为运行时依赖 | 🟡 **待定，见 O2**。图中标的是工具类比，不是选型结论 |
| 新的告警系统（Grafana / Alertmanager） | Discord webhook 已在用且已验证端到端。需求是「有人知道」，不是可观测性平台 |
| 审计 M1 的模型质量 | 那是 L3 的评估口径，失败模式是「数字对但结论站不住」，不是本篇的尺度 |
| 城市专有字面量进通用层 | 护栏 §1。PK、冬季 `type` 清单等一律从 `config/` / `contracts/` 读 |

## 5. 交付物（草稿级）

| # | 交付物 | 说明 |
|---|---|---|
| 1 | 规则清单（配置驱动） | 一条规则 = 表 + 维度 + 断言 + 严重级（`error` / `warn`）+ 等值或下界。**落配置不落代码** |
| 2 | `dq_audit_log` 表 | 唯一的新表。一次运行一批行；至少含 run_id / 检查 id / 表 / 维度 / 实测值 / 期望 / 通过与否 / 耗时 |
| 3 | 独立 DAG | 自己的 cron，**不挂在 Gold 构建之后**（日频 vs 手动，L2 O8 已定） |
| 4 | 打标机制 | `certified` / `suspect` 的载体未定，见 O3 |
| 5 | 手动全量入口 | 回填之后、Silver 开跑之前跑一次 |

第一批实现 = **L2 的 O8**（两个 Bronze 探针进 `dag_audit_bronze`）。
