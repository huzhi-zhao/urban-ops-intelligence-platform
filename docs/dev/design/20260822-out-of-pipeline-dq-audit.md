## 1. 为什么单开一篇：L3 里没有这件事

先回答「L3 是不是已经包含它」。**不包含。**
L3-c（[scoring-chain-and-m1 §3](20260820-scoring-chain-and-m1.md)）交付的是：

> 每张表记录行数 · 各列空值率 · 分区完整性 · 构建耗时 …… L1/L2 跑完的当时
> 就分别记进各自的 launch，L3 只做汇总 + 补测试四件套。

这是**一次性的基线快照**，性质上属于「管道内 + 上线门禁」：它在构建的那一刻
测一次，写进 launch 文档，没有调度、没有第二次、没有趋势、没有跨层对账、
没有对下游的打标。它是本篇的**输入**（阈值的唯一依据），不是本篇。

真正属于「管道外」的碎片今天散在三个地方，谁都不拥有它：

| 碎片 | 现在在哪 | 状态 |
|---|---|---|
| Bronze 内容正确性（校验 B 分片内唯一 / 校验 C 上游行数对账） | 复盘附录 + L2 的 **O8** | ✅ **已进调度**（`a5304cb`） |
| Silver 分区完整性 | L2 **O7** —— 挂在 Gold 构建器的前置检查里 | 只在手动构建 Gold 时才跑 |
| 逐列空值率、行数基线 | L1/L2 launch 的一次性实测 + L3-c 汇总 | 静态数字，无人复测 |

**本篇把这三块合成一件事，并从 L3 拎走一部分。**

### 1.1 与 L3 的边界（拎走 / 留下）

| | 归属 | 理由 |
|---|---|---|
| DQ **基线**（一次性测量 + 写进 launch） | **留在 L3-c** | 它是上线门禁的一部分，跟着那次构建走 |
| 测试四件套（`unique` / `not_null` / `relationships` / `accepted_values`） | **留在 L3-c**（管道内），但**本篇复用其实现**复跑 | 断言本身是结构性的，属管道内；「今天再跑一遍」才是管道外（§4.1） |
| **定时复测、趋势、跨层对账、计分卡、certified/suspect 打标** | **本篇** | 需要「多次运行之间比较」，L3 只跑一次 |
| Bronze 校验 B/C 进 `dag_audit_bronze`（L2 **O8**） | **本篇接管** | ✅ 已完成，是本篇的第一批 |

## 2. 管道内 vs 管道外

平台已有的所有质量手段都在管道内。两类的差别不是检查项，是**权力**：

| | 管道内（in-pipeline） | 管道外（out-of-pipeline） |
|---|---|---|
| 谁跑 | ETL job / Gold 构建器自身 | 独立 DAG，自己的 cron |
| 何时 | 写盘前 | 数据**已经落盘之后** |
| 失败后果 | **抛异常，数据不落盘** | 只报告与打标，**不阻断** |
| 能看见 | 本次窗口 / 本次构建 | 跨批次、跨层、跨时间 |
| 已有实现 | `assert_unique` · `enforce_schema` · `spatial_hit_rate` · Gold 的精确行数门禁（R4） | Bronze 校验 B/C（第一批已落地） |
| 典型漏网 | 慢性漂移、静默停更、跨表不一致 | 无法阻止坏数据进 Gold |

> 一句话：管道内回答「这一批能不能写」，管道外回答「已经写下去的这一堆，
> 今天还成立吗」。**分页无序那次故障两边都该抓、两边都没抓**——管道内的
> `assert_unique` 只覆盖被跑到的窗口，管道外根本不存在。

### 2.1 本篇不动管道内的任何一条

现有的管道内断言**全部保留原样**，一条都不迁出来。理由：它们的价值恰恰
在于「不落盘」，搬到管道外就退化成事后通知。本篇是**增加一层**，不是重构。

## 3. 六个维度（对齐流程图）

四个大类，落到六个维度的计分卡。**每一条都必须能回答「谁修、修什么」**，
不能回答的不进清单。

### 3.1 结构性 DQ —— 查「形状对不对」

| 检查 | 说明 |
|---|---|
| Schema / Type | 落盘的 Parquet 列与 `sql/ddl/` + `contracts/` 三方一致 |
| NULL | 契约声明 `nullable: false` 的列真的没有空值 |
| Duplicate | PK 重复行。**PK 从契约派生，不写在 DAG 里**（复盘附录第 1 条） |
| Required Fields | 关键字段是否整列缺失 |

⚠️ 与管道内重叠是**有意的**：管道内只看被跑到的窗口，管道外覆盖全部历史。
2019 之前那 9 个窗口全绿并不能说明那些天干净。

### 3.2 统计性 DQ —— 查「量级对不对」

| 检查 | 说明 |
|---|---|
| Row Count | 行数与历史区间对比 |
| Null Rate | 空值率突变（基线来自 L3-c 的逐列实测，**全空列 0，七列非零空值已有语义解释**） |
| Distribution | 均值 / 分位数漂移 |
| Freshness | 最新分区日期是否停更 |

🔴 **Freshness 只查分区存在性，不查行数。** O17 定案：上游 311 发布滞后约一天，
08-18 当天只有 8 行，同一天再问是 3,006。**「偏薄」是稳态，「没有」才是缺口**——
把偏薄当缺口就是造一个天天响然后被静音的告警。

🔴 **空间命中率一律走 `zone_assignment.spatial_hit_rate()`，分母是 `has_geo` 子集。**
上游 79% 无坐标，全表口径的阈值永远报警。这条已经是 L1 的定案，审计层不得另算。

### 3.3 业务性 DQ —— 查「意思对不对」

| 检查 | 说明 |
|---|---|
| KPI Checks | 指标口径与 BO 定义一致 |
| Range / Logic | 值域、时序先后（`closed_ts_utc >= open_ts_utc`） |
| Plausibility | 数字像不像真的 |

这一维是**最容易写成主观题**的一维，因此要求：每条业务断言必须指向一个
BO 编号或一个 launch 里记过的实测数字，否则不写。已有的可用锚点举例：
`dim_plow_zone` 25/8/3 · `fact_parking_ban` 49（19 匹配 / 30 NULL，
**语义不是缺数据**）· F1 的非零格 **下界 ≥ 880**（908 是实测，916 已失效）。

### 3.4 跨层对账（本流程独有）

三层都已落盘才比得了，这是管道内做不到的一件事：

- **Bronze → Silver**：原始行数 −（去重数 + 隔离数）是否守恒。
  已有锚点：全量首次落地时 Bronze = Silver = **12,474,313**，拒绝行 0。
  🔴 **分母不是 18.4 M**（那是上游整表；Bronze 采集范围有意不是全历史）。
- **Silver → Gold**：明细求和 vs 聚合值是否一致（roll-up）。
  已有锚点：Gold 建表当时 Silver 行数 12,477,414 与建 Gold 时逐行相同。
- **Bronze ← 上游**：即复盘附录的**校验 C**，唯一能发现丢行的一层。
  容差**只给最近 N 天**（迟到工单），历史天不给。

> 🔴 **重复与丢失在行数上相互抵消**（复盘 §结论①），所以扫描（校验 B）与
> 对账（校验 C）**缺一不可**，不能因为「行数对得上」就省掉一层。

### 3.5 计分卡与闭环

- 按六维汇总通过率与趋势，落 **`dq_audit_log`** 表（§5.1）。
- 所有 `error` 级检查通过 → Gold 打标 `certified`，下游放心消费；
  否则 → 告警 + 人工复核，Gold 标 `suspect`，看板挂「数据待核实」。
- FAIL 之后走**根因分析 & 规则迭代**：源系统坏了？转换逻辑错了？还是规则过严？
  → 修复回填走 CLI（**审计不改数据**），更新规则后重跑审计。

🔴 **规则过严是三个候选里最可能的一个**，且是唯一一个「修 Gold 修不好」的。
上面 F1 的例子就是：门禁写 916、实测 908，错的是门禁不是表。
**迭代规则也是闭环的合法出口**，不是失败。

## 4. 三条细化时新定的通则

初稿留给「逐条决定」的东西，实际写规则时发现有通则可循。先定通则，
再写清单，否则几十条规则会各自长成一个样子。

### 4.1 复用 `dq_assertions.py`，不重写第二套断言引擎

`scripts/gold/dq_assertions.py` 已经在做「从 DDL 头注生成断言 → 连 Trino 执行 →
报 violations」，L3-c 用它跑出 185 条 / 0 violations。管道外要的东西是它
**加上三件事**：结果落表、与上一次运行比较、不抛异常。

因此结构性维度**不写新 SQL**：调用同一个模块，把返回值喂进 `dq_audit_log`。
断言本身仍归 L3-c 所有（改断言去改 DDL 头注），本篇只是第二个消费者。

🔴 **`dq_assertions` 的「可空列只在非空行上检查」这条语义必须原样继承。**
否则 `fact_winter_event_zone_load.rank_factor` 那 924 个设计上就该空的格会
报成违反，七条已知空值全变假警报，基线随即被静音。

### 4.2 管道外**一律不用等值**行数门禁

初稿的 O4 写的是「能抓构建故障的保持等值，随上游回修漂移的给下界」。
这条在**管道内**是对的（`scripts/gold/gates.py` 照旧），在管道外是错的，
理由是两者的时点不同：

- 管道内的等值门禁跑在**这一次构建刚结束**时，期望值和实测值来自同一次构建，
  等值有意义——它抓的是「purge 没清干净导致行数翻倍」这类构建故障。
- 管道外**天天跑**，而 Gold 会被重建、上游会追加数据、Open-Meteo 会回修历史
  存档导致 `segment_events` 重切。**等值期望值在下一次重建后必然失效**，
  于是要么天天误报，要么每次重建都得改配置——两条路都通向静音。

因此管道外的行数检查一律写成两条，都不是等值：

| 形式 | 抓什么 | 例 |
|---|---|---|
| **绝对下界**（写死，来自基线） | 表塌陷 / purge 后没写进去 | `fact_service_request_zone_event >= 12,000` |
| **环比变化率**（对 `dq_audit_log` 上一次运行） | 慢性漂移、突变 | 变化 > ±10% → `warn` |

**绝对下界取基线的 90%，取整到可读的数**，不是精确值。它不是用来抓 1–2 行
漂移的（那是环比的活），它抓的是「表空了」「只写进最后一个 chunk」这种量级故障。

🔴 **这不是把门禁放松了。** 精确等值仍然存在，只是留在管道内它该在的地方。
管道外拿到的**趋势**是管道内原理上给不了的东西——这正是 `dq_audit_log`
存在的全部理由：「没有它就只有『今天过没过』，没有『是不是在变坏』」。

### 4.3 不对 Silver 做全表扫

O13 的墙还在：`silver_service_request` 12,477,414 行 / 4,878 个日分区，
七个真实列的全表扫**实测 read timeout**（gold-sql.md 开头那张表）。
Trino 是平台级共享服务，连接参数不归本仓库调。

所以统计性与业务性检查的目标是：

- **Gold 侧 17 张表**——全部很小（最大 141,377 行）、无分区，L3-c 实测一次
  跑完 17 张表 **2.8 秒**。这是审计的主战场。
- **Silver 侧只走滚动窗口**（14 天），且只查分区存在性与该窗口内的行数。
- **Bronze 侧**沿用已落地的校验 B/C 与它们自己的滚动窗口。

## 5. 交付物（第二批）

范围按 ADR 0012 §6 的分批走。**本轮只做第二批**，第三批（跨层对账 + 计分卡 +
打标实现）另开一篇 launch。

### 5.1 `dq_audit_log` —— 唯一的趋势载体

`sql/ddl/dq_audit_log.sql`，每条检查一行：
`run_id / layer / table_name / rule_id / dimension / severity / observed / expected /
comparator / passed / rows_checked / rows_failed / elapsed_s / checked_at`。

🔴 **这张表是追加型，不走 R4 的整表重建。** 它是 17 张 Gold 表之外唯一一张
`INSERT` 只追加、永不 `DROP` 的表——重建它等于每天把趋势抹掉，而趋势是它
存在的唯一理由。DDL 头注必须写清楚这一点，否则下一个人会「顺手统一」掉它。

### 5.2 新 schema `uoip_meta`

审计自己的表**不进 `uoip_gold`**。理由是具体的，不是洁癖：
`build_gold.TABLES`、`dq_baseline.py`、`dq_assertions.py` 都在「遍历 Gold 的
每一张表」，多一张非业务表进去就要在三处各加一次排除，漏一处就是审计表
被当业务表 purge 掉。隔离一个 schema 的成本是 `.env` 多一个变量。

`hive.uoip_meta` 承载：`dq_audit_log`（本轮）+ `gold_certification`（第三批）。

### 5.3 规则清单 `config/dq/rules.yaml`

一条规则 = `id / layer / table / dimension / check(内置类型或 sql) /
comparator(>= | <= | between | pct_change) / expected / severity(error|warn) /
cadence(daily|weekly|manual)`。**落配置不落代码**（护栏 §1：业务语义不进通用层）。

本轮填入的规则，全部有实测锚点：

| 维度 | 规则 | 值的来源 | 形式 |
|---|---|---|---|
| 结构性 | 17 张 Gold 表四件套复跑 | `dq_assertions` 185 条 | `rows_failed = 0`，`error` |
| 统计性 | 每张 Gold 表行数 | L3-c 基线 17 个数 | 下界（基线 90%）+ 环比 ±10% |
| 统计性 | 零行的表 / 全空的列 | 基线：**各 0** | `= 0`，`error` |
| 统计性 | 七列已知空值率 | §3.2 的七个数 | 环比 ±5 个百分点，`warn` |
| 统计性 | 其余列空值率 | 基线 0% | `= 0`，`error` |
| 统计性 | Silver 最新分区 freshness | O17 | `<= 2 天`，只查存在性 |
| 业务性 | F1 非零格 | 908 实测 | `>= 880`，`warn`（会随回修漂移） |
| 业务性 | 空间命中率 | 99.8988% / has_geo 分母 | `>= 99.5%`，`error` |
| 业务性 | `closed_ts_utc >= open_ts_utc` 等值域 | 契约 | `rows_failed = 0`，`error` |

### 5.4 执行器与 DAG

- `scripts/dq/run_audit.py` + `make dq-audit`（手动入口，含 `--full-sweep`）。
- `dags/dag_dq_audit.py`，日频，跑在 **Airflow 容器内**（连 Trino 用容器视角
  `trino:8080`，不写 `localhost:8090`）。
  🔴 **finding 不 fail 任务**，只有「检查跑不起来」才 raise（ADR 0012 §1 规定 2）。
  **不写 `on_failure_callback`**——`DEFAULT_ARGS` 已有，写了就是覆盖掉它。

### 5.5 单测

规则解析 · comparator 语义 · 「管道外没有任何一条等值行数规则」的钉子
（对应管道内那条 `test_only_the_live_upstream_number_is_a_lower_bound`）·
DAG 部署契约（`days_ago` 不可用 / `sql/` 要挂进容器 / 不得 `from dags._dag_common`）。
DAG 本身进 `make test-dags` 的 `.venv-airflow`。
