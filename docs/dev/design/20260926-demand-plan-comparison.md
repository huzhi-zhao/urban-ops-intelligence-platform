## 0. 与伞篇 R6 原定义的三处差异

| | 伞篇 R6（2026-09-21） | 本篇 | 理由 |
|---|---|---|---|
| 需求侧 | 「需求分」= 预测请求量 + 天气 | **M1 预测请求数** + **每千地址请求率**，不是分数 | 天气已是 M1 的输入，再加一次是重复计入；且它在事件内是常数（方差 99.73% 在事件之间，§3.3），对事件内比较贡献为零 |
| 计划侧 | 「计划差距」= 需求排名 − 排班排名 | **计划班次原值 1–5** | 5 个并列值减一个 1–22 的名次是在制造精度（ADR 0015 §3 第 2 条） |
| 两者的关系 | 两个指标 | 两栏并排 + 一条**复核提示规则**（§3.3） | 排名差被否决后，「哪些格值得看」需要一条显式规则来回答 |

## 1. 问题

- 伞篇 §3.6：`load_score` 的事件内排序由班次决定（台阶 5.77 分 vs 台阶内 0.106 分），
  所以 F6 / F7 回答不了「计划与需求对不对得上」。
- 能回答这个问题的三样东西 Gold 里**都已经有了**，只是从未被放在一起：
  `fact_request_forecast.predicted_count` / `actual_count`（需求估计与实际）·
  `fact_event_zone_rank.shift_number`（计划）· `dim_plow_zone.address_count`（强度的分母）。
- 伞篇 R6 自标「必要」，但它的原定义在落地时站不住（§0），需要重写。

## 2. 约束

**契约冻结。** 自 2026-08-13 起（`CHANGELOG.md` v1.0）。新建 Gold 表要走 AGENTS.md
「Data contract obligations」五步。本轮不走，产出落在 `sql/presentation/`。

**`sql/presentation/` 三条硬约束**（[README](../../../sql/presentation/README.md)）：
纯 Trino SQL 一条语句；头注三键必写；`carrier: lookup` 的 SQL **只出计数不出比率**。
→ 每千地址率由页面构建步骤算，SQL 只出 `predicted_count` 与 `address_count`。

**dashboard §10.2 七条规则**，与本篇直接相关的四条：回测与预测分开标注 ·
不确定性与点估计同框 · 不替换 `#/zone` 已有的两个答案 · 不越过「现在」。

**F5 的预测对训练季是样本内拟合。** `scripts/models/train_m1.py` 的
`_predict_scoring_era` 用一次训练（`holdout_last_season`，留出 2025-2026）的系数，
预测全部 1,298 个排班期格。59 个排班期事件里**只有 7 个**是留出，其余 52 个的
`predicted_count` 模型训练时见过答案。F5 **没有列**区分这两种格。

**F5 里同时存在多个 `model_version`**，包括故意训坏的 `nomonth`。
版本串字典序会选中它（L3 launch §4.6）。

**排班源没有「计划更新时间」。** 契约
[`winnipeg-plow-shifts.yaml`](../../../contracts/api-contracts/winnipeg-plow-shifts.yaml)
只有六个字段：`id` · `snow_ban_id` · `shift_number` · `shift_start` · `shift_end` ·
`plow_zone`。能给的只有两个日期：作业本身的开始时间（`dim_plow_event.first_shift_start_utc`，
计划的**内容**）与本项目的采集日期（`source_max_ingest_date`）。

**覆盖面是固定的**，四种格状态（§3.2）的行数由现有门禁钉死，不需要新量。

## 3. 方案

### 3.1 产出与粒度

一份新的展示查询，暂名 `fig_bo8_03_demand_plan_panel.sql`，`carrier: lookup`，
`schema: gold`。**粒度 = F5 的粒度** `(snowfall_event_id, plow_zone, model_version)`，
每个版本 1,298 行（59 个排班期事件 × 22 个分区）。

| 列 | 来源 | 说明 |
|---|---|---|
| `snowfall_event_id` · `start_date` · `end_date` · `total_snowfall_cm` · `snow_season` | `dim_snowfall_event` | |
| `plow_zone` | F5 | |
| `model_version` | F5 | 输出全部版本，与 `fig_bo1_03` 同一做法；由页面构建步骤**显式**钉一个（§3.8） |
| `predicted_count` · `actual_count` | F5 | 原样透传 |
| `address_count` · `address_count_snapshot_date` | `dim_plow_zone` | 分母与它的单一时点，后者必须随行出现 |
| `fit_role` | 派生 | `snow_season = '2025-2026'` → `holdout`，否则 `in_sample`。字面量与 `fig_bo1_03` 同源，构建步骤断言它等于模型产物里的 `holdout_season` |
| `plow_event_id` · `first_shift_start_utc` | `dim_plow_event` | **经由 `dim_plow_event` 连接**，不直接用 `fact_event_zone_rank.matched_snowfall_event_id`（该列头注的扇出警告） |
| `shift_number` | `fact_event_zone_rank` | 无匹配作业时为 NULL |
| 三张源表各自的 `etl_run_id` · `source_max_ingest_date` | 各表 | 来源栏 |

认证状态不在 SQL 里取：沿用冻结路径附带的认证状态（dashboard §10.2 ⑤）。

### 3.2 四种格状态

页面对每一格恰好落在一种状态。状态由数据决定，页面文案按状态写死：

| 状态 | 格数 | 页面显示 | 🔴 不得显示 |
|---|---:|---|---|
| 计划 + 估计 | 374（17 × 22） | 两栏 + 复核提示 | —— |
| 仅估计：该事件没有匹配的公开作业 | 924（42 × 22） | 估计；计划栏写「这场雪没有公布的全市作业，无从对照」 | 零差距、或任何暗示「没清雪」的措辞（ADR 0014 §1.1：没发布不等于没作业） |
| 仅计划：作业没对上任何降雪事件 | 44（2 × 22） | 不在 F5 粒度里。方法说明列出这两次作业，`#/zone` 已有它们的顺位 | 估计值 |
| 都没有：3 个无排班分区 | 3 个分区 × 全部事件 | 「这个分区没有公布过班次」，也没有估计（M1 面板只有 22 区） | 估计值 |

前两行之和 = 1,298，与 F5 行数相同，是 §5 的第一条门禁。

### 3.3 复核提示规则

对一个事件里**同时有计划和估计**的 22 格，一格得到提示，当且仅当：

1. **需求强度高**：按每千地址预测率（`predicted_count / address_count × 1000`），
   在本事件的 22 格里排进前 **K** 名；
2. **班次靠后**：`shift_number ≥ S`；
3. **稳定**：在 R13 的重采样副本里，该格进本事件前 K 名的比例 ≥ **P**。

三个参数落 `config/`，不写死在代码里（城市无关护栏 §1：「5 个班次」本身是城市实例）。
规则的求值放在 `scripts/presentation/`，用角色名，带单测。

**默认值：K = 5 · S = 4 · P = 0.8**（2026-09-27 登记，先于任何真实数据求值）。
🔴 **改默认值要在本篇留痕并写明理由**，不得在看到提示结果之后调——与伞篇 §3.5
「判据先定，免得看到数再找理由」同一条纪律。

**为什么用强度（率）而不是总量（请求数）：** 后排分区地址更多是已知事实——
分区平均顺位与地址数 `r = +0.491`（十年），2021 年起 `r = +0.403`（BO-2 反证清单，
图 `FIG-BO2-04`）。
按请求数排，提示会**按构造**落在大而靠后的分区上，等于把一条已知的相关性重新发现一遍
然后叫它「需求」。而率正是 M1 自己的量：`log(address_count)` 是 offset，
`predicted_count / address_count` 就是模型估计的每地址率。

**为什么提示用估计而不用实际计数：** 用估计，提示本身**可以被打分**——
事后看被提示的格实际率是否也高；页面并排给出实际计数，读者自己能看到提示有没有
兑现。用实际计数，提示就没有东西可对，模型也退成摆设。
⚠️ 这个打分只检验**需求那一侧**：被提示的格需求确实高，不说明计划应该改。

规则的措辞是提示不是结论，文案与 ADR 0015 §4 的四条禁语同步。

### 3.4 对 R13 的接口

R6 向 R13 要的**只有一样东西**：每个 `model_version` 一份重采样副本，长表，

| 列 | 说明 |
|---|---|
| `replicate_id` | |
| `snowfall_event_id` · `plow_zone` | 覆盖 1,298 个排班期格 |
| `predicted_mean` | 该副本重拟合后在**真实面板**上的预测均值 |

外加元数据：副本数 B · 随机种子 · 簇单位（事件）· 被扰动的 `model_version` ·
特征是否固定。落在与 F5 artefact 同一族的位置（`gold/_forecast_runs/{model_version}/` 下），
**不进 Gold 表**。

要原始副本而不是现成的区间，理由是 §3.7：稳健性分析要扫多个 K，
若 R13 只交某一个 K 的比例，每换一个 K 就得重跑一次重采样。
R6 自己从副本算两样东西：

- 每格的区间（分位数）；
- 每格在各个 K 下进本事件前 K 名的副本比例（按率排序）。

🟡 **副本给的是「均值」的不确定性，不是「请求数」的。** 页面把区间与实际计数并排，
读者会把它读成请求数的范围，而均值的区间在计数面前必然偏窄。见 §6 第 4 项。

### 3.5 样本内与留出

`fit_role` 随行输出（§3.1），页面按它分两种标注：

- `holdout`：「回测估计：模型训练时没见过这一季」；
- `in_sample`：「样本内拟合：模型训练时见过这场雪的实际计数」。

🔴 **样本内的格不给复核提示。** §3.3 说提示能被打分，前提是估计是在不知道答案的
情况下做出的；样本内的估计已经拟合过实际计数，拿它去「预言」高需求再用实际去验证，
是循环论证。

这让留出季里**有公开作业的事件数**变成承重的数：它决定页面上有多少格能出现提示。
该数目前未知，§6 开工前查询的第一条就是量它。

**R2 在这里多了一个用途**：滚动起点评估每一轮都会对被考的那一季产生样本外预测。
R2 落地后，页面的估计可以改用「每一季都由此前各季训练出来的模型预测」的那一份，
`fit_role` 增加一个取值，能出提示的格从一季扩到每一季。
这是 R2 本身的副产品，**不是 R6 要求 R2 做的额外工作**。

### 3.6 R5 关闭

R5 问 `shift_number / 5` 与 `(shift_number - 1) / 4` 哪个更贴语义。本篇里班次以原值
1–5 出现在计划栏，以阈值 S 出现在提示规则里，**不被缩放进任何数**，R5 失去对象。
F6 的 `/5` 保持不动：F6 已退为历史方法（ADR 0015 §2.1 ①），为一个不再扩展的表改尺度，
只会让一张已认证的表与它的已发布数字对不上。

### 3.7 R4 换对象

权重随分数一起消失；K / S / P 是新的先验数字。伞篇 R4 的判据原样平移过来：

- 扫一个网格：**K ∈ {3, 5, 8} × S ∈ {4, 5} × P ∈ {0.7, 0.8, 0.9}**，共 18 组；
- 报**在全部 18 组下都被提示的格**（稳健集），以及每组的提示数分布；
- **不报「哪组参数更好」**——这一层依然没有答案可对（伞篇 §0）。

原 R4 在 F6 权重上的四套对比**不做**：F6 已退为历史，且伞篇 §3.6 已预判了结果
（「一套 vs 三套」），在一个不再扩展的分数上验证一个已知结构，不值得花时间。

### 3.8 页面契约

- **版本**：页面构建步骤必须显式接收服务版本（同 F6 的 `FORECAST_VERSION=`），
  多于一个版本而未指定时**拒绝构建**。三种「自动选」全都错，理由同 L3 launch §4.6。
- **日期**：只出现「作业开始于 …」（计划内容）与「本项目采集于 …」（数据日期），
  🔴 不出现「计划最近更新于」。
- **两条路径**：
  - 分区优先（居民）：地图选分区 → 选一场过去的雪 → 计划 → 来源 → 估计。
    顺序是故意的：先公开记录，后模型。不做地址输入（ADR 0013 §4 第 3 条）。
  - 事件优先（复核者）：选一场雪 → 22 个分区一张表：估计（带区间）· 率 · 班次 · 提示 · 实际。
- **位置**（2026-09-27 定）：作为 **`#/zone` 里的一节**，排在该页已有的两个答案**之后**。
  居民路径天然从分区进入；复核者的「一场雪 22 个分区」视图作为这一节里的展开表，
  不另开页面。`#/zone` 已有的两个答案一字不动（§10.2 ③），新一节有自己的标题与回溯声明，
  不与「照抄上次」的规则答案混写。首页两条核心发现仍排在任何模型内容之前（§10.3）。
  dashboard 需求 §10.3 在 C 组同步改写。
- 回溯声明与官方工具指引沿用 `#/zone` 现有文案与单测
  `test_the_page_does_not_present_itself_as_the_city_status_tool`。

### 3.9 分批

回滚粒度不同，分三批，批间停下等确认：

| 批 | 内容 | 依赖 | 对外可见 |
|---|---|---|---|
| **A** | §3.1 的查询 + 台账登记 + 冻结导出 + §5 的 A 组门禁 | 无 | **否**。只有冻结导出，不上页面 |
| **B** | 从 R13 副本算区间与前 K 比例；§3.3 规则求值；§3.7 的 18 组网格 | R13 按 §3.4 交付 | 否 |

A 组不等任何人，可以立刻开工。**提示在 B 之前一个都不存在**——没有稳定性，
第 3 条规则无从求值，而不带稳定性的提示违反 dashboard §10.2 ②。

## 4. 被否决的选项

1. **「计划差距 = 需求排名 − 排班排名」**：并列值上制造精度。ADR 0015 §3 第 2 条。
2. **需求分里保留天气**：天气已是 M1 输入，且事件内是常数，只抬高分数水平、不改变
   事件内比较。F6 的 `demand_weather_only` profile 在事件内本来就等于纯 M1 排序（伞篇 R6）。
3. **按请求数（总量）做提示**：按构造偏向大而靠后的分区（§3.3）。
4. **新建 Gold 表**：契约冻结，且唯一的消费者是页面。等出现第二个消费者再提（§6 第 6 项）。
5. **在 F6 里加一个 profile**：改动一张已认证表的语义，并且把能打分与不能打分的数
   重新放进同一张表——正是 ADR 0015 要拆开的东西。
6. **提示用实际计数**：提示变得不可检验，模型退成摆设（§3.3）。
7. **样本内的格也给提示**：循环论证（§3.5）。
8. **提示不带稳定性、先上页面再补**：违反 dashboard §10.2 ②；且一个没有稳定性的
   「前 K 名」恰好是伞篇 R13 说的「在假装名次没有抽样误差」。

## 5. 验收判据

**A 组**（对冻结导出执行，钉死的版本记为 `$V`）：

| 判据 | 期望 |
|---|---|
| `model_version = $V` 的行数 | **1,298** |
| 其中 `shift_number IS NOT NULL` | **374**，且 `COUNT(DISTINCT snowfall_event_id)` = **17** |
| 其中 `fit_role = 'holdout'` | **154**（7 × 22） |
| SQL 里的留出季字面量 | 等于 `$V` 模型产物的 `holdout_season` |
| `SUM(predicted_count)` | 与 F5 同版本逐位相同（透传没有改数） |
| 查询输出里没有比率列 | 单测（`lookup` 只出计数） |
| 头注 `fig_id` 在台账里 | 既有单测 |

**B 组**：

- 副本元数据齐全（§3.4），B 与种子记录在导出里；
- 18 组网格全部求值，稳健集与分布一起报出；
- 样本内格的提示数 = **0**（§3.5，单测）；
- 区间的类型与在留出格上的实际覆盖率一起报出（§6 第 4 项）。

**C 组**：

- 四种格状态各有一个单测，文案与 §3.2 表逐字对齐；
- 多版本未指定时构建拒绝（单测）；
- 页面文本不出现 `forecast`（回测场景）与 `updated`（单测）。

### 开工前查询（第一轮，只有这一条）

留出季里有多少个事件对上了公开作业。它决定第 3 项，也决定页面上最多能有多少格出提示。

```sql
SELECT
    e.snowfall_event_id,
    e.start_date,
    e.total_snowfall_cm,
    p.plow_event_id,
    p.first_shift_start_utc
FROM hive.uoip_gold.dim_snowfall_event AS e
LEFT JOIN hive.uoip_gold.dim_plow_event AS p
    ON e.snowfall_event_id = p.matched_snowfall_event_id
WHERE e.snow_season = '2025-2026'
ORDER BY e.start_date
```

预期 **7 行**（留出季的 7 个事件）。判据先定：

- `plow_event_id` 非空 **≥ 2 行** → 按本篇原方案走，提示只出现在这几个事件上；
- **恰好 1 行** → 页面上只有一个事件能出提示，第 3 项要明确「一个事件够不够」；
- **0 行** → 没有任何一格同时有公开计划和不知道答案的估计，第 3 项必须在 B 组前定。

⚠️ 表名全限定是故意的，理由同伞篇 §3.5：手跑时没有 session schema。

**实测（2026-09-27）**：7 行，命中预期；`plow_event_id` 非空**恰好 1 行**——
`SNOW-20251218`（2025-12-18，16.17 cm，作业 `37458073`，首班 2025-12-21 13:00 UTC）。

该季另一次作业 2026-02-26 本来就是两次未对齐之一。
