# Design Docs

一篇 design doc 记录**一次变更打算怎么做**：问题 → 方案 → 被否决的选项 → 约束 → 验收判据。

写给三个月后的人。判据是：**三个月后重读，这一段还有用吗？** 没有就删掉，
它多半属于 [PR 描述 / Code Review / Commit / Ticket comment](../README.md#二不要写进-design-doc-的东西)。

---

## 与 ADR 的边界

两者都记录取舍，最容易混。区别在**范围**，不在篇幅：

| | ADR | Design doc |
|---|---|---|
| 对象 | 一个**选型**：用 A 还是 B | 一次**变更**：这件事怎么落地 |
| 影响面 | 跨变更、跨模块，后续所有工作受它约束 | 限于这一次变更 |
| 例子 | 用 MinIO 还是 GCS | 怎么把现有代码从 GCS 迁到 MinIO |
| 生命 | 被后一篇 ADR 取代 | 上线后由对应的 launch 记录接管 |

**同一件事经常两篇都要有**：ADR 定"选 MinIO"，design doc 定"分几批迁、什么顺序、
怎么算迁完"。design doc 里凡是"为什么选它"的段落，都应该只留一句结论 + 链到 ADR。

## 命名

```
design/YYYY-MM-<topic>.md
```

`YYYY-MM` 是**开写的月份**，不是上线月份，写定后不改。
`<topic>` 用能力名，不用城市名、不用票号（票号进 Ticket，见根 README）。

同一主题的第二轮设计**新开一篇**（`2026-09-<topic>-v2.md`），
在旧篇顶部标 `Superseded by <新篇>`，不原地改写。

---

## 状态标记

顶部必须有一行：

```
> **Status**: Draft | Accepted | Superseded by <file> | Abandoned · **Date**: YYYY-MM-DD
```

`Accepted` 之后正文冻结。上线过程中的实际偏差记在
[launch/](../launch/README.md) 里，不回写 design doc——
两篇的差异本身就是有价值的信息。

## 模板

```markdown
# <变更名>

> **Status**: Draft · **Date**: YYYY-MM-DD

## 1. 问题
现状是什么，为什么现在必须动。用可观测的事实陈述，不写"不够优雅"这类判断。

## 2. 约束
硬约束（资源上限、不可重放的数据、上游 API 限制）与显式接受的风险。

## 3. 方案
做什么、分几批、每批的边界在哪。**不列逐文件清单**——那是 PR 描述。

## 4. 被否决的选项
每个附一句否决理由。这一节的价值最高，也最容易被省略。

## 5. 验收判据
可执行的判据优先（一条 grep、一条 SQL、一个行数断言），
"看起来正常"不算判据。

## 6. 开放项
还没定的事 + 建议 + 什么时候必须定下来。
```

## 附：数据源相关的变更，剖析结论必须回答这五个问题

新接一个数据源或改动清洗逻辑时，第 3 节之前先补一段剖析结论。
下面这张表是从已归档的 `bronze-data-exploration.md` 中提炼的，
与查询引擎无关（原文的 BigQuery 外部表 SQL 已随 GCP 失效）：

| 要回答的问题 | 决定什么 |
|---|---|
| 主键是什么？是否唯一？ | Silver 层去重键（7 天回溯窗口必然重复拉取，不定死会累积） |
| 时间字段是什么格式？时区？有无异常值？ | 分区键选择、UTC 标准化逻辑 |
| 哪些字段 NULL 率高？ | 默认值 / 过滤策略；**空间命中率告警的分母** |
| 哪些字段基数低？ | 适合做聚合维度与聚簇键 |
| 与其他源怎么关联？ | Gold 层 JOIN 键设计 |

方法论层面（为什么先探查再写 transform）见
[ADR 0004](../adr/0004-silver-cleansing-methodology.md)。
