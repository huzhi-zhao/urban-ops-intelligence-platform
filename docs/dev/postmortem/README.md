# Postmortems

一篇 postmortem 记录**一次已经造成影响的故障**：发生了什么、影响面、
根因、为什么没有被更早发现、改什么才能让这一类不再发生。

- [Bronze Socrata 分页无序](bronze-socrata-pagination-incident.md) —— 窗口式抓取漏了 `$order=:id`，页边界重复行（并可能丢行）进了 311 全量 Bronze。
- [Silver 写入 commit 阶段被误判为挂死](silver-commit-stall-incident.md) —— 对象存储 rename 无日志且耗时 2.5 小时，两次跑批被人为中断，并留下一条错误的「疑似 OOM」归因。

---

## 什么时候必须写

不是"出错就写"。判据是**影响是否已经发生且不可当场撤销**：

| 情形 | 写不写 |
|---|---|
| 数据永久丢失或缺口无法回补 | **必须**（本项目最典型的是 BO-7 快照漏采——覆盖式数据集，漏一天永久少一天） |
| 错误结果已经进入 Gold 或被外部读到 | **必须** |
| 上线过程中发现并当场解决 | 不写，记在 [launch/](../launch/README.md) 第 2 节 |
| 开发期发现、未上线 | 不写。若暴露的是通用规则，升格进 `CLAUDE.md` / `AGENTS.md` |
| 一次性环境问题、手滑 | 不写，Ticket comment 即可 |

`CLAUDE.md` 的 **Escalate to human when** 一节列的四种情况，
若已经造成上述影响，都需要一篇 postmortem。

---

## 命名

```
postmortem/<topic>-incident.md
```

`<topic>` 描述**受影响的能力**，不用日期、不用票号、不用人名。
同一能力二次故障：`<topic>-incident-2.md`，并在第一篇末尾链过去——
重复故障说明第一篇的改进项没落地，这个链接就是证据。

---

## 模板

```markdown
# <能力> 故障复盘

> **Date**: YYYY-MM-DD · **Detected**: YYYY-MM-DD HH:MM · **Impact**: <一句话>

## 1. 影响
数据 / 结论 / 使用方，各受了什么影响。可量化的必须量化（缺了几天、几行、
哪个区间的结果不可信）。可恢复与不可恢复分开写。

## 2. 时间线
从"实际出问题"到"发现"到"止血"到"恢复"。
**"实际出问题"与"发现"之间的间隔是本篇最重要的数字。**

## 3. 根因
一直问到能被修掉的那一层为止。技术根因与流程根因分开写。
**排查途中被推翻的归因照写**，附推翻它的证据——否则下一个人无法判断
某条路径是没试过还是试过不通。每个数字带测量时间、测量入口与测量环境。

## 4. 为什么没有更早发现
监控缺失 / 阈值不对 / 告警发出但无人看见 / 分母算错导致长期误报被忽略。
这一节通常比第 3 节更有价值。

## 5. 改进项
| 改什么 | 类型（止血 / 防复发 / 早发现） | 落到哪（PR / Ticket / ADR / 规则文件） |
每条必须有确定的去处。**"以后注意"不是改进项。**
```

---

## 写作纪律

- **对事不对人。** 记录"部署流程允许跳过校验"，不记录"谁跳过了校验"。
- **不写进度、不写追责、不写道歉。** 改进项的执行状态在 Ticket 里跟踪，
  不回写本篇——postmortem 写完即冻结。
- **冻结不排斥更正。** 根因后来被更深的实测推翻时，在原处追加带日期的更正块，
  原文不动；结论整体变了才另写一篇。
- 若复盘推翻了某个技术选型，另写一篇 ADR，本篇只链过去。
