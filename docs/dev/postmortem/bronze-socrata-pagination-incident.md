# Bronze Socrata 分页无序 故障复盘

> **Date**: 2026-08-18 · **Detected**: 2026-08-18 14:42（L1 阶段 E 全量回填第 10 个窗口）
> **Impact**: `SRC-WPG-311` 的 Bronze 存量中存在分页边界造成的重复行，
> 且**同一机制会造成无法被任何现有检查发现的丢行**。已扫描：34 个分片多出 38 行，丢行量未知。

## 1. 影响

**已确认**：`bronze/raw/SRC-WPG-311/service_requests/2019-06/data_2019-06-07.ndjson.gz`
（3,585 行，跨 4 页）中，`case_id=103d95de… / interaction_id=101012333164`
一行**字节级重复两次**。该文件内只此一个重复键。上游实测该键只有一条记录
（同 `interaction_id` 的另一条 `case_id` 不同，属正常的一通电话派生两个 case），
故重复是**采集侧制造的**，不是上游数据形态。

**全量扫描结果（2026-08-18，`scripts/profiling/bronze_duplicate_scan.py`）**：

| 数 | 值 |
|---|---|
| 分片总数 | 4,878 |
| 多页分片（> 1000 行） | 4,511（92.5%） |
| 带重复的分片 | **34**（占多页分片 0.75%） |
| 多出的行 | **38** |
| 重复行是否字节级相同 | 全部是 |
| 单页分片中的重复 | **0** |

单页分片零命中、脏分片全部字节级相同——两条都与分页假说一致，没有反例。
脏分片随页数升高而变密：2019–2022 的 2–3 页分片零星命中，2025-09 之后的
4–5 页分片明显密集。页边界越多，撞上的机会越大。

> ⚠️ **34 和 38 是下界，不是影响面。** 同一根因的另一半是**丢行**：页边界移位
> 既能让一行出现两次，也能让一行一次都不出现。丢掉的行在分片里不留任何痕迹
> ——没有计数对不上、没有校验和异常，manifest 里的 `sha256_checksum` 描述的
> 正是那份已经少了行的载荷。所以**一个"干净"的多页分片不构成任何证据**，
> 而"干净"的多页分片有 4,477 个。唯一的确认手段是与上游对行数（见 §5）。

**未受影响**：Silver / Gold 一行都没写进去——`assert_unique` 在写盘前抛出。
L1 阶段 E 前 9 个窗口（雪季窗口）跑完的分区数据本身有效，但它们同样来自
未修复的 fetcher，可信度与上面同一条：不能因为断言没响就认为它们完整。

## 3. 根因

**技术根因**：Socrata 的 limit/offset 分页在结果集无序时不保证行序。
`$order=:id` 只加在了全表walk 分支，窗口分支漏了。**过滤不会让结果集变得有序**
——这是当时判断中缺的那一步：写注释的人正确地识别了风险，但把风险归因给了
"全表walk 很长"，而真正的条件是"跨页"。311 单日 3,585 行，天天跨页。

**流程根因**：`5b7b14a` 修的是"static 源一行都取不到"这个眼前故障，
`$order=:id` 是顺带加的正确补丁。修一个具体故障时，**没有反问同一份文件里
另一条代码路径是否有同样的问题**——两个分支相隔 30 行。

## 4. 为什么没有更早发现

- **Bronze 侧没有任何唯一性检查**。`dag_audit_bronze` 核对的是"分区在不在、
  manifest 有没有"，不核对分区**内容**是否自洽。重复行和丢行都不改变分区存在性。
- **manifest 的校验和防不住这个**。`sha256_checksum` 描述的是我们写下去的载荷，
  不是上游应有的载荷；采集时就重了/少了，校验和会忠实地确认那份错误载荷完整无损。
  它保证的是"传输与存储没出错"，从来不保证"取的是对的"。
- **它最终是被下游一层的断言发现的**，而且是被 Silver 的 PK 断言**顺带**发现的
  ——那条断言是为"上游变更"设计的，不是为"采集缺陷"设计的。
  它抓到了，属于运气好的一侧：换成丢行，这条链上没有任何一环会响。
- 探针阶段（任务 3）跑出的 311 空间命中率 134,123/134,258 走的是**直连 API 的
  取数层**（`scripts/analysis/_probe_common.py`），不经这条 fetcher，
  所以探针数字与 Bronze 的分歧不会以任何形式暴露出来。

## 附：Bronze 完整性校验方案（待实施，本篇只记录）

> 本节是 §5 中「`dag_audit_bronze` 增加完整性核对」那一条的展开，
> **尚未实施**，落地时按此写 design 篇。放在复盘里是因为方案的每一条
> 判据都直接来自这次故障暴露的盲区，脱离本篇会看不出为什么这么定。

### 为什么现有的审计不够

`dag_audit_bronze` 今天核对的是**分区在不在**：扫 manifest，缺哪天补哪天。
这一层对「采集根本没跑」有效，对「跑了，但取回来的东西不对」完全无效——
重复行和丢行都不改变分区的存在性，manifest 的 `sha256_checksum` 又只保证
「我们写下去的字节没坏」，不保证「我们取回来的行是对的」。
这次 34 个脏分片在现有审计下全部显示健康。

### 三层校验，代价与能力递增

> 编号用 **A / B / C**，不用 L1/L2/L3 —— 后者在本项目里已经指三次上线
> （L1 Silver 全链路 · L2 Gold 维表 · L3 评分链），两套编号撞名会读错。

| 层 | 查什么 | 代价 | 能发现 | 发现不了 |
|---|---|---|---|---|
| **A 存在性**（已有） | 分区 / manifest 在不在 | 列对象 | 采集没跑、整天缺失 | 内容错误 |
| **B 分片内唯一性** | 分片内 PK 是否唯一 | 解压 + 计数，不出网 | 重复行 | **丢行** |
| **C 上游行数对账** | Bronze 行数 vs 上游 `count(*)` | 每天一次轻量 HTTP | **丢行**、重复行 | 内容被改写（同数不同值） |

校验 B 就是 `scripts/profiling/bronze_duplicate_scan.py` 已经实现的能力，
搬进 DAG 即可。**校验 C 是唯一能发现丢行的一层**，也是这次真正缺的那一层——
没有它，这次故障影响面的下半截永远只能写「未知」。

### 落地时必须遵守的四条

1. **PK 字段从契约派生，不写在 DAG 里。**
   `(case_id, interaction_id)` 是 `SRC-WPG-311` 的实例知识，硬编码进
   `dag_audit_bronze` 就是把城市专有字面量塞进通用层（城市无关护栏 §1）。
   参照批 1 的做法：审计目标已经改为从 registry 按 `partition_strategy` 派生，
   PK 应同样落在 `config/sources/*.yaml` 或 `contracts/` 里由 DAG 读取。
   **没有声明 PK 的数据集就跳过校验 B**，不猜。
2. **`snapshot` 源只报不补，与现有规则一致。**
   上游不留历史，「补」只会把今天的状态写进过去某天、伪造历史。
   校验 B/C 对 snapshot 同样只报警不重拉——这条现有 DAG 已经做对了，别在扩展时丢掉。
3. **校验 C 的容差要按 7 天回溯窗口给。**
   311 有迟到工单，最近几天的上游 count 本来就会往上走。把正常的迟到
   当成丢行会制造一个天天响的告警，然后被静音——那正是 CLAUDE.md 里
   「分母算错导致长期误报」那条护栏说的事。**容差只给最近 N 天，历史天不给。**
4. **只审计当天窗口 + 滚动窗口，全量扫描单独跑。**
   4,878 个分片的全量校验 B 是分钟级、校验 C 是数千次请求，不该每天做。
   日常审计走滚动窗口（与现有 14 天 / 3 个月一致），全量作为手动入口，
   在回填之后、Silver 开跑之前跑一次。

### 不做什么

- **不在审计里去重、不在审计里改 Bronze。** Bronze 不可覆写（AGENTS.md）。
  审计的产出是一份重拉名单，重拉走 CLI，与三层回填架构一致。
- **不把校验 B 挪进 Silver job 代劳。** `assert_unique` 已经在 Silver 拦了一道，
  但它在**写盘前**才拦，且只覆盖被跑到的窗口——这次 2019 之前的 9 个窗口
  全绿并不能说明那些天干净。审计要覆盖全部 Bronze，与 Silver 跑没跑无关。
