# 跨机房对象存储访问 故障复盘

> **Date**: 2026-07-30（部署成型日）· **Detected**: 2026-09-01（真因确认）
> **Impact**: 计算节点与存储节点分处两个机房，所有对对象存储的访问都要跨广域网。
> 该布局造成了两次已发生的故障——Silver 全量重跑的 commit 阶段耗时 2.5 小时并
> 被人为中断两次、Trino 全表扫描 4,878 个分区直接 `Read timed out`——而两次的
> 归因都停在了「对象存储没有原生 rename」「分区数太多」这一层，**没有一次点到
> 跨机房这个共同的放大系数**。

## 1. 影响

**已发生且不可当场撤销的部分是架构与判断，不是数据。**

- **一条错误的前提写进了 ADR 并长期有效**。ADR 0006 §2.1 论证存算分离时写的是
  「在本项目的数据量级（单作业 1–2 GB）下网络不是瓶颈」。这个论证只考虑了
  **传输量**，没有考虑**往返次数 × 单次时延**，而后者才是本项目两次故障的成本
  来源。该句自 2026-07-30 起被当作已论证的结论引用。
- **两次已记录的故障各自被归因到了症状层**：
  - [Silver 写入 commit 阶段被误判为挂死](silver-commit-stall-incident.md)——
    38,688 个对象的 copy + delete 往返耗时约 2.5 小时。原篇根因写的是
    「对象存储没有原生 rename」，这是对的但不完整：同样的对象数在同机房内是
    另一个量级的耗时。
  - `.claude/rules/gold-sql.md` 记的 Trino 全表扫描 `Unable to execute HTTP
    request: Read timed out`（2026-08-19，4,878 个分区）。原文把墙定性为
    「分区数，不是行数也不是吞吐」——方向是对的，但没有说清为什么 4,878 这个
    数量级就撞墙：单次往返越贵，能在 socket 超时内排完的对象数就越少。
- **代价已经固化进设计**：`gold-sql.md` 的 R1（必带日期谓词）与 R2（分年切块）
  是为绕开这堵墙而立的规则，`fact_winter_request_daily_by_label` 至今只能分块
  构建。这些规则本身是对的，但它们的**成本参数被记成了常量**，而实际上它是
  部署布局的函数。
- 时间成本：两次无效的 Silver 跑批（各 2–3 小时机时）+ 2026-08-19 一轮诊断
  往返（`$partitions` 与 `COUNT(*)` 被误当作「数据可读」的证据）。

**未受影响**：没有数据丢失、没有错误结果进入 Gold。17 张 Gold 表的行数经多次
重建逐张一致。这是一次性能与归因故障，不是正确性故障。

## 2. 时间线

| 时点 | 事件 |
|---|---|
| 2026-07-30 | ADR 0006 定存算分离。两节点实际落在**两个机房**：计算节点（4c/24G ARM，Airflow + Spark + Trino + Hive Metastore + Superset）与存储节点（MinIO）不同城。ADR 只写了「两个独立节点」，未记录地理分布，也未把它列为一项成本 |
| 2026-08-18 | 症状一：Silver 全量重跑 commit 阶段静默 90 分钟以上，两次被人为中断。归因落在 rename 语义上，收篇 |
| 2026-08-19 | 症状二：Trino 全表扫描 4,878 个分区 `Read timed out`。归因落在分区数上，立 R1/R2 规则绕开 |
| 2026-09-01 | 在为另一个项目做硬件拓扑设计时被指出：两节点分处两个机房。三条观测（commit 慢、全表扫超时、一年 365 分区秒回）在这个前提下第一次落到同一个根因上 |

**从布局成型（2026-07-30）到真因被识别（2026-09-01）间隔约一个月**，
其间该布局已经导致两次可记录的故障，每次都被独立归因、独立绕开。
这个间隔不是由问题的难度造成的，是由**没有人把两次故障放在一起看**造成的。

## 3. 根因

**技术根因**：对象存储的访问模式是**大量小往返**，不是少量大传输。

- Trino 读 Parquet：先读 footer，再按列按行组发 range GET。一次全表扫描对
  4,878 个对象发出的请求数是**数万量级**，且这些请求要在 S3 客户端的 socket
  超时内排完。
- Spark 的 `FileOutputCommitter`：每个输出对象一次 copy + 一次 delete。
  38,688 个对象就是约 77,000 次往返。

两者的成本都是 **往返次数 × 单次往返时延**，与传输的字节数几乎无关。
跨机房把单次往返时延抬高一个量级，就把这两条路径的总耗时同样抬高一个量级。
ADR 0006 §2.1 的论证用的是**传输量**这个维度，因此对这两条路径完全无预测力——
它的结论（「网络不是瓶颈」）在它自己选的维度上甚至是对的。

**流程根因**：**部署事实没有进入设计文档**。ADR 0006 记了两节点的职责边界、
容量、备份策略，唯独没记它们在哪。于是后续每一次排查都缺一个关键输入，而且
缺得没有痕迹——读 ADR 的人不会意识到自己少了一条信息。

第二层是**故障之间不做关联**。8-18 与 8-19 两次故障相隔一天，症状都是
「对象存储访问异常地慢」，但分别记在 postmortem 与 rules 两处，没有任何一处
提示它们可能同源。

## 4. 为什么没有更早发现

- **两次症状都有一个足够合理的局部解释**，且这两个解释本身是正确的：对象存储
  确实没有原生 rename，墙确实是分区数。一个正确但不完整的根因比一个错误的根因
  更难被推翻，因为它经得起复核。
- **没有任何一处记录过节点的物理位置**，因此「跨机房」这个变量在整个排查过程中
  从未出现在候选列表里。
- **RTT 从未被测量过**。项目对存储侧的观测只有可用性（能不能连上）与容量，
  没有时延。而时延正是这两条路径的唯一成本参数。
- **一年 365 分区秒回**这条观测反而起了掩盖作用：它证明了「不慢」，于是把注意力
  引向了分区数的绝对值，而不是引向单位成本。

## 5. 改进项

| 改什么 | 类型 | 落到哪 |
|---|---|---|
| ADR 0006 §2.1 补记两节点的地理分布，并更正「网络不是瓶颈」这句的适用范围（它只对传输量成立，对往返次数不成立） | 防复发 | ADR 0006 追加更正块（已做） |
| `.claude/rules/gold-sql.md` 的实测表补记跨机房这个前提，使 R1/R2 的成本参数可被后来者正确解读 | 防复发 | 规则文件（已做） |
| [silver-commit-stall-incident.md](silver-commit-stall-incident.md) 追加更正块，指向本篇 | 防复发 | 该篇（已做） |
| 实测存储节点 RTT 与单次 GET 时延，作为今后一切分区粒度决策的输入 | 早发现 | 待办 |
| 今后任何跨节点的部署决策，必须在 ADR 里写明节点的物理/网络位置，并把往返成本与传输成本分开论证 | 防复发 | ADR 模板约定，待办 |

> 🔴 本篇不推翻存算分离这个选型本身——分离的收益（计算节点可重建而不牵连数据）
> 与节点放在哪无关。被推翻的是**「分离的网络代价可忽略」**这条论证。
> 若后续要重新评估节点布局，另写 ADR，本篇只提供成本依据。
