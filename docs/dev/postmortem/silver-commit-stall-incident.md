# Silver 写入 commit 阶段被误判为挂死 故障复盘

> **Date**: 2026-08-18（定性日）· **Detected**: 2026-08-18 阶段 D 第三次跑批途中
> **Impact**: `dag_backfill_silver_weather_archive` 的全量重跑被**人为中断两次**，
> 每次损失约 2–3 小时机时；两次中断的原因被记成「疑似 OOM」，这个未经验证的猜测
> 进了台账并**误导了后续的排查方向**（差点去调内存参数，而正确方向是 commit 算法）。

## 1. 影响

**已发生且不可当场撤销的部分是判断，不是数据。**

- 两次跑批在 `Start to commit write Job …` 之后被杀。`FileOutputCommitter`
  未走完，最终路径下**一个对象都没落成**——复数前缀 `silver/snowfall_events/`
  事后实测 0 个对象。故没有半成品数据、没有脏分区，**数据面零影响**。
- 受影响的是**记录**：台账里两次失败挂着「一次误操作、一次疑似 OOM 未确认」。
  这条错误归因存活到第三次跑批，是本篇的实际损失。
- 时间成本：两次无效跑批 + 一次为验证而重来的完整 3 小时 03 分。
- 顺带被掩盖的问题：`sync_partition_metadata` 缺失（写进去了但 Trino 查不到）
  长期没被注意到，因为写入本身慢得看不出时间差。

**未受影响**：Gold 无数据、无外部读者；第三次跑批一次通过，
`silver_snowfall_event` 159 行，对账闭合。

## 2. 时间线

| 时点 | 事件 |
|---|---|
| — | 前两次补测在 job 1 完成后的 commit 阶段被中断，记为「误操作 / 疑似 OOM」 |
| 2026-08-18 | 阶段 D 第三次跑批。job 1 完成，耗时 1316 s（22 分钟） |
| +0 min | 日志停在 `Start to commit write Job 2cc5a734-…`，此后**90 分钟无任何输出**，Airflow task 持续 `running` |
| +90 min | 改为取正面证据：`ps` 看 Java 进程 TIME、`docker stats` 看 NET I/O、隔 60 s 数两次对象数 |
| +92 min | 读数：`Sl`、CPU ~5%、TIME 持续增长、对象数在 38,384 ~ 38,688 之间波动 → 判定**在干活**，不杀 |
| +183 min | 全程 3 小时 03 分完成，一次通过 |

**从"实际慢"到"知道它只是慢"的间隔 = 两次跑批 + 90 分钟**。
这个间隔全部由「没有判活手段」造成，而不是由问题本身的难度造成。

## 3. 根因

**技术根因**：对象存储没有原生 rename。`silver/weather_archive/` 下有
**38,688 个对象**（约 9,700 个日分区 × 4），`FileOutputCommitter` 把每个对象
从 `_temporary` 挪到最终路径都是一次 copy + delete 往返 MinIO。
几万次往返 ≈ 2.5 小时，且**这段路径不打日志**。
3 小时 03 分里 job 1 只占 22 分钟，其余全在 commit。

该成本**随分区数线性增长**，是选分区粒度时的一项成本，不只是查询性能问题。

**流程根因**：中断决策的依据是「太久没动静」，这是**缺乏证据的推断**，
不是观测。当时手上没有任何一条判活手段，于是"看起来像挂了"直接等价于"挂了"。
第二层是**记录纪律**：把猜测写成结论。「疑似 OOM」里的"疑似"两个字，
在下一次读台账时被自动丢掉了。

## 4. 为什么没有更早发现

- **Spark 的 commit 阶段静默**。job 完成会打日志，commit 开始会打一行，
  然后到结束为止什么都不打。进度条、计数器、stage 视图在这一段全部无信息。
- **Airflow 侧只有二值状态**。`running` 既表示"在算"也表示"卡死"，
  task 层面没有任何心跳可看。DAG 失败告警（`_alerts.py`）也只在**失败**时响，
  对"活着但看不出在动"这一类完全无覆盖。
- **没有基线**。此前 Silver 只跑过窗口式的小批，从未在近 4 万对象的表上 commit 过，
  所以"多久算异常"没有可比数字，只能凭感觉，而感觉给出的答案是错的。
- **台账没有区分观测与推断的字段**。一旦写下去，猜测和事实长得一样。

## 5. 改进项

| 改什么 | 类型 | 落到哪 |
|---|---|---|
| 判活三件套写进运行手册：`ps -o pid,stat,etime,time,pcpu -C java`（TIME 涨不涨）· `docker stats`（NET I/O）· 隔 60 s 数两次对象数 | 早发现 | `docs/dev/launch/20260817-silver-etl-runnable-launch.md` §2 阶段 D2 / §3.3（已落） |
| **杀掉长跑任务前必须有正面证据**（进程在耗 CPU / 存储在变化），"太久了"不构成依据 | 防复发 | 本篇 + launch 篇 §5 |
| E 阶段开跑前评估 `mapreduce.fileoutputcommitter.algorithm.version=2`（省掉 `_temporary` → 最终路径那一轮 rename）；不启用则明确重估预期耗时 | 止血 | L1 launch 篇 §5，`service_request` 18.4 M 行、日分区跨十年，分区数远多于气象存档 |
| 补 `sync_partition_metadata`——Spark 走 s3a 直接写文件不经 Hive Metastore，19 个窗口跑完 Trino 侧全是假 0 且**不报错** | 早发现 | L1 launch 篇 §5（E 阶段前置） |
| 台账里的失败原因未经验证时，"疑似 X" 必须同时写清**验证它需要哪一条观测**；不写就不许写猜测 | 防复发 | 本篇写作纪律，沿用 postmortem README「对事不对人」的同一层 |

> 一条判断，不属于改进项：**D4「先确认新的有数据，再删旧前缀」这个顺序不改。**
> 这次实测复数前缀下 0 个对象，担心的风险并不存在，顺序等于白排。
> 但它的价值不在于这次用上了——反过来做，只要有一次前两次跑批**恰好** commit 成功过，
> 就没有第二次机会。
