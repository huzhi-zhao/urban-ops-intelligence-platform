### 2.3 否证与保留

> 一轮跑下来被推翻的猜想记在这里。**否证是正常产物**，不是意外。

1. 🔴 **0.668 是一个算错的 Spearman，不是「另一个口径」。** 前后期切法**相同**
   （探针 `rank_counterfactuals.py:224` 的 `half = 19 // 2 = 9`，与 Q3 的 9/10 一致），
   唯一差异是并列秩：Q3 用 `RANK()` 的**最小秩**，而 Spearman 的定义要求**平均秩**
   （`_probe_common.spearman` 正是 Pearson-over-averaged-ranks）。这份数据并列很多
   （F/N 都是 2.00，J/L/I/R 都是 1.89），最小秩把它们全压到同一个位置，
   相关系数被系统性抬高。**台上只用 +0.591**，2026-08-30 已逐位复现。
   🟡 不为此在 Trino 里再实现一遍平均秩：一个数只留一个权威口径，那就是探针。
2. ⚠️ **C2-6 的「2 次」是 lag 7d 口径。** 探针曾按 `--align-lag-days 3` 给出过
   一份**四条**的名单（2019-02-10 / 2021-01-07 / 2021-11-27 / 2022-11-24），
   已在 2026-08-09 更正。Gold 的 `is_aligned` 用的是宽 lag——实测对齐延迟可达
   17 天（2021-11-27 ← `SNOW-20211110`）。**图注若提到「对不上」，必须同时说 lag**，
   否则同一件事有两个数。
3. 🟡 **`fact_plow_shift` 里没有 2017 和 2023 年的犁雪事件。** 19 次作业跨
   2015-12 → 2026-02，中间两个年份为空。**尚未查证**是真的没有全市作业，
   还是上游那两年的禁令记录缺失。时间轴类图**不许把它画成一条连续的线**。
4. 🟢 **「每次犁雪的末班只有一个分区」是结构，不是巧合。** Q11 实测 19/19 个事件
   都排满 5 个班次，所以第 5 班必然恰好一格；能排到第 5 班的只有 A/B/C/D/E 五个分区
   （Q1 的极差列 `1-5`），第 4 班再加一个 V。三条独立查询自洽。
5. ✅ **`ban_type_id` 的名称已落实**（B11，上游只读一次）：`1` ANNUAL SNOW ROUTE ·
   `2` EXTENDED SNOW ROUTE · `4` RESIDENTIAL (KNOW YOUR ZONE)，恰好三组、无 `3`，
   与契约逐字一致。⚠️ **Gold 与 Silver 都取不到这个映射**（`description` 在 Silver
   被丢弃），所以它是**文档里的字面量**，不是可重跑的查询——改了要回上游重取。
6. ✅ **被否证的猜想（本轮无新增）。** 探针阶段否证的三条（吹雪风积 / 冻雨 /
   单点气象代表性，见 CLAUDE.md BO-3 遗留）属于 BO-3，记在 §4。

### 3.3 否证与保留

1. 🔴 **「按分区」的图必须先声明是 25 还是 22。** crosswalk、边界、行政标签覆盖
   **25** 个分区（含 `X` / `B/D` / `Downtown` 三个无排班分区）；排班顺位只覆盖
   **22**。同一张幻灯片上两个分区数不加说明地并存，读者会以为其中一个是错的。
2. 🔴 **B3 的份额是「面积占比」，不是台账里那个 34.1%。** 后者是**工单标签一致率**
   （分区→ward 45.4%），量的是「工单自报的 ward 和它所在分区的主导 ward 是否相同」，
   分母是工单不是面积。⚠️ 巧合的是分区 **A 的面积主导份额恰好是 0.3412**——
   **不要把这两个 34.1% 对上**，它们是两个不同的量。
3. 🟡 **4 个 neighbourhood 落不进任何分区**（237 − 233），名字是
   `perrault` · `the mint` · `trappistes` · `west perimeter south`（B8）。
   **成因仍未知**：四个都是市域边缘或极小的地名，但「在犁雪分区覆盖之外」只是猜想——
   `dim_admin_label` 来自工单自报文本、`dim_region_crosswalk` 来自几何相交，
   两者本就不保证同一个论域。**在查清之前不许把 237 讲成「全部纳入」**。
4. ✅ **`WINDROW` 为零已定性为数据事实**（B9）：它映到 1 个 type
   `Snow Removal Windrow Inquiry`，观测期内没有工单。分类图**可以上台**，
   但图注必须写「该类别在观测期内无工单」——一个恒为零的类别在饼图里是空的、
   在堆叠图里是隐形的，不写会让读者以为这一类不存在。
   🟢 顺带它是 O4「最具体优先」生效的证据：这个 type 名里带 `Snow Removal`，
   按「SNOW 优先」会被 SNOW 吞掉。
5. ⚠️ **PLOW / ICE_CONTROL / WINDROW 的 `priority_weight` 是 NULL，实测按 1 兜底**
   （B9 + B10）：三类的 `weighted_request_count` **精确等于** `request_count`。
   **不是归零，BO-6 的需求项确实覆盖六类。** 但 1 是 1–3 量表的**下限**，于是
   PLOW（4,074 条，第二大类）与 ICE_CONTROL 被默认按最低优先级计入，而 SANDING
   的加权比接近 2、SNOW 1.29。**没有人做过这个决定**——它是种子表三类没填权重的

### 4.3 否证与保留

1. 🔴 **`severity_score` 里没有时长，但它看起来有。** 定义是降雪量与低温各半
   （在 99 个事件上各自 min-max 归一，`sql/dml/dim_snowfall_event.sql:57`），
   而实测与 `duration_days` 的相关 **0.828** 高于与它自己那一半降雪量的 **0.760**。
   **图注必须写出定义**，否则读者会「确认」一个错的因果（严重 = 下得久）。
   🟡 上限只到 0.90：没有哪个事件同时是最大降雪和最低温。
2. 🔴 **lag 有两个锚点，相差 10 天，两个数都对。** 已直接证实（launch §15.3）：
   2021-11-27 那次匹配 `SNOW-20211110`，事件起 11-10、讫 11-20，首班 11-27——
   **从起算 17 天，从讫算 7 天**。CLAUDE.md 的 17 与 E4 的 7 是同一件事。
   **凡引用 lag 必须写明锚点**，BO-3 固定用「事件结束起算」（「雪停之后多久开始犁」
   才是运营问题）。
3. ✅ **「累积判据救回了无降雪犁雪」现在可以说，但只能说四分之一**（E4b）：
   2022-11-24 匹配到 `SNOW-20221118`（`accum_flag = true`，峰值 1.0 cm），
   2021-11-27 是宽 lag 救的，**2021-01-07 与 2026-02-26 仍然开着**。
   完整表述见 launch §15.2 的四行表。✅ 归因已直接确认（launch §15.3），不是反推。
   🟡 值得同框讲的对比：救回 2022-11-24 的那个事件全期只有 **1.8 cm**，
   而 2021-11-27 那次是 **26.2 cm**——同样触发全市犁雪，降雪量差 14 倍。
4. 🔴 **N = 99 里混着「事件」和「事件的尾巴」，不要讲成「99 场雪」。**
   trailing 10 日窗口在大雪之后**还会继续命中十天**，而 `gap_days = 1` 把这条尾巴
   **切成独立事件**：三个 accum 事件的全期降雪量只有 0.2 / 1.0 / 1.4 cm，
   其中 `SNOW-20221115`（0.2 cm）与 `SNOW-20221118` 相隔 3 天被切开，
   两者是同一场雪的尾巴。⏳ 这几个微量事件与 C3-9 那 11 个零工单事件是否重合，
   未量（launch L13）。
   🟢 **但这不推翻 C3-12**：CLAUDE.md 查清的成因本来就是阈下累积（21 日累计保留
   对照组 76%，单日峰值只保留 26%），**匹配到一段尾巴恰恰是这条机制的正确表现**。
5. ⚠️ **雪季无空档 ≠ 犁雪无空档。** 2017 与 2023 没有犁雪事件（§2.3 保留 3），
   而降雪事件 18 季齐全。两张时间轴放在一起时必须分别标注。
