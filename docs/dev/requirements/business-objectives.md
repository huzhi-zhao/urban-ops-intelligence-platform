# 业务目标

> **v2 — 2026-07-29**，当前部署城市从 NYC 切换为 **Winnipeg (MB)**，全部 BO 重写。
> 数据依据来自 [winnipeg-data-sources.md](winnipeg-data-sources.md)
> 的实测结果（2026-07-29 实际调用 SODA API）。
>
> BO 的定义保持**城市无关**：「服务请求」「作业分区」「行政区」都是角色名。
> 下文括号里的 311 / Plow Zone / Ward 是**当前 Winnipeg 部署**的具体实例，
> 换城市时替换实例、不改目标。

---

## 0. 业务场景

温尼伯自嘲为 "Winterpeg"。除雪预算超支、除雪投诉、停车禁令规则混乱
每年都是市议会与本地新闻的固定议题（如 CBC 报道 2023 年除雪超预算 **420 万加元**）。

市政的冬季运营调度每天需要回答三个问题：

1. 哪些社区/选区在本次降雪事件中**服务负荷最高**？
2. 负荷高的**原因**是什么——降雪量大、作业未覆盖、还是响应超时？
3. 下一次降雪应如何**调整分区作业优先级与资源投放**？

现状：需求侧（311 投诉）、供给侧（犁雪排班/禁令）、驱动侧（气象）
三类数据分散在不同端点，且**使用三套互不对齐的地理口径**，缺少统一平台。

### 0.1 与官方工具的边界（划定范围的前提）

市政府已提供 **Know Your Zone** app 与**近实时除雪进度地图**，
回答的是「我家这条街清了没」——**当前状态、单点查询**。

> 🚫 **本项目明确不做**：除雪状态查询地图、分区查询 app、实时进度看板。
> 与官方产品重复，无增量价值。

本项目做官方工具**不做**的部分：**回溯性、跨源、可问责的运营分析**。

## 1. 核心业务目标

### BO-1 · 冬季服务请求负载监控（需求侧）

> 每个社区/选区在冬季承受多大的服务压力？

**数据依据【实测】**：`u7f6-5326` 311 Requests，全表 18,346,621 行，
其中冬季运营相关 **275,243 条**（占 1.50%），带地理信息 **220,580 条**（占冬季的 80.1%）。
时间跨度 2008-06-17 ~ 至今，覆盖 **18 个冬季**。

**指标定义**：

| 指标 | 定义 |
|---|---|
| 冬季工单量 | 按 `type` 关键词匹配的日/事件级计数，按 neighbourhood / ward 聚合 |
| 加权工单量 | 按 `type` 内嵌的官方优先级加权（P1 = 3、P2 = 2、P3 = 1） |
| 平均处理时长 | `closed_date` − `open_date`，按优先级分组 |
| 负载异常 | 单日工单量 > 该社区 30 天滚动中位数的 150% |

**验收标准**：

- 冬季工单识别规则覆盖 `%SNOW%` / `%FROZEN%` / `%PLOW%` / `%SANDING%` /
  `%WINDROW%` / `%ICE CONTROL%` 六类，且**不误伤** `Serv-ice` / `Pol-ice` /
  `Not-ice` / `Invo-ice`（曾因粗糙匹配误得 10.40%，真值为 1.50%）
- 242 个 neighbourhood、15 个 ward 均能产出日度序列

**已知约束**：见 §2.1（地理缺失）、§2.2（渠道口径漂移）。

### BO-2 · 除雪作业执行追踪（供给侧）

> 每次降雪之后，市政实际做了什么、覆盖了哪些分区、什么时候做的？

**数据依据【实测】**：

| 数据集 | 规模 | 内容 |
|---|---|---|
| `mfzv-893p` Snow Parking Bans | **49 条** | 禁令决策日历，含 `ban_start` / `ban_end` / `ban_type_id` |
| `tix9-r5tc` Plow Zone Schedule | **418 条** | 作业排班，含 `shift_start` / `shift_end` / `plow_zone`；**19 个禁令事件 × 22 个分区**，覆盖 2015-12-19 ~ 2026-02-28 |

两表通过 `mfzv-893p.id` ↔ `tix9-r5tc.snow_ban_id` 关联。

**指标定义**：

| 指标 | 定义 |
|---|---|
| 事件覆盖度 | 单次禁令事件覆盖的 plow_zone 数 / 22 |
| 作业时长 | `shift_end` − `shift_start`，按分区 |
| 决策滞后 | `ban_start` − 降雪峰值时刻 |

**验收标准**：19 个事件全部能与气象数据对齐并产出上述三项指标。

> ⚠️ **供给侧远比需求侧稀疏**：11 年仅 19 次住宅区犁雪事件。
> 这直接决定了分析设计必须是**事件驱动**而非投诉驱动，见 §3。

### BO-3 · 降雪驱动因子

> 多大的降雪会触发多少服务需求？触发市政发布禁令的阈值是什么？

**数据依据【实测】**：Open-Meteo Archive API，坐标 `49.895, -97.138`，
字段 `snowfall_sum`(cm) / `temperature_2m_min` / `temperature_2m_max`，
日粒度，历史存档已验证可用。**平台已有 `SRC-Open-Meteo` client，零成本接入。**

**指标定义**：

| 指标 | 定义 |
|---|---|
| 降雪事件 | 连续日 `snowfall_sum` 累计 ≥ 阈值（阈值待标定，初值 5 cm） |
| 严寒日 | `temperature_2m_min` ≤ −25 °C（关联冻管、冻结雨水口工单） |
| 天气严重度 | 降雪量 + 低温的归一化复合评分（0–1） |

**验收标准**：能给出「降雪量 → 投诉量」的剂量反应曲线，
并标定出市政发布禁令的经验阈值。

> 注：这里**不做天气预测**。Open-Meteo 提供预报，平台只是消费它。
> 规则触发 → 提前调配建议，是 if-else 不是模型。

### BO-4 · 三套地理口径的空间对齐（基础能力）

> 需求侧、供给侧、行政侧用的是三套不同的几何，必须先对齐才能做任何关联分析。

**这是本项目最硬的工程前提，也是 NYC 部署不存在的新问题。**

| 口径 | 粒度【实测】 | 来源 | 用途 |
|---|---|---|---|
| `neighbourhood` | **242 个** | 311 字段 | 需求侧最细粒度 |
| `ward`（选区） | **15 个** | 311 字段 | 问责与政治单元 |
| `plow_zone`（犁雪分区） | **22 个** | `tix9-r5tc` / `39ur-higg` | **供给侧唯一口径** |

**三者互不嵌套**：plow_zone 不是 ward 的细分，也不是 neighbourhood 的合并。
必须用 `39ur-higg` 分区边界与 311 的 `geometry` 点做 `ST_CONTAINS` 空间 JOIN，
才能把投诉归属到犁雪分区。

**指标定义**：

| 指标 | 定义 |
|---|---|
| 空间命中率 | 有 `geometry` 的工单中成功落入某 plow_zone 的比例 |
| 交叉映射表 | `dim_geography` 需同时承载 neighbourhood / ward / plow_zone 三种归属 |

**验收标准**：

- 空间命中率 > 90%（分母为**有地理信息的工单**，不是全表——见 §2.1）
- 产出 neighbourhood ↔ plow_zone 的面积加权映射表
- 命中失败降级为 `neighbourhood` 文本字段，仍不可解析则标记 NULL 并排除出评分

**已知数据质量问题**：ward 名 `Daniel McIntyre` 与 neighbourhood 名
`Daniel Mcintyre` 大小写不一致，字符串匹配会漏；必须以空间 JOIN 为准。

### BO-5 · SLA 合规性审计（核心差异化交付物）

> 市政承诺的 P1/P2/P3 除雪时限，实际达成率是多少？各社区之间是否公平？

**这是官方工具完全不做的部分，也是论文最有分量的贡献点。**

**数据依据【实测】**：311 的 `type` 字段（3,563 个取值）
**直接内嵌了官方的优先级与时段口径**：

```
Snow Removal Street Priority 1 Reg          Sanding Request Priority 2 After
Snow Removal Sidewalks Priority 3 After     Frozen Catch Basin Priority 1 Reg
Snow Removal High Piles Pr 2                Snow Removal Request Sidewalk After Hours P1
```

意味着**可以用市政自己的口径**做合规性分析，无需自行定义标准。
官方分级政策：https://winnipeg.ca/publicworks/snow/snow-clearing-policy.stm

**指标定义**：

| 指标 | 定义 |
|---|---|
| SLA 达成率 | `closed_date − open_date` ≤ 官方承诺时限的工单占比，按 P1/P2/P3 分组 |
| 响应时长分布 | 各优先级的 P50 / P90 处理时长 |
| 空间公平性 | 各 neighbourhood / ward 的 SLA 达成率离散度 |

**验收标准**：

- 完成 3,563 个 `type` 取值的归一化字典，正确解析出优先级与时段维度
  （需处理 `Pr 2` / `Priority 2` / `P2` 三种写法及 `_vof` 后缀变体）
- 从官方政策文档提取 P1/P2/P3 的承诺时限，形成可引用的基线
- 产出按 ward 的 SLA 达成率排名

> ⚠️ **前置依赖**：`closed_date` 的业务语义需验证——
> 它是"工单关闭"还是"实际清雪完成"？若是前者，SLA 结论需谨慎表述。
> 见 §4 待办。

### BO-6 · 冬季运营负载评分（最终交付物）

> 每个社区/选区在每次降雪事件中一个综合评分，直接驱动资源调度建议。

三路 Silver 数据汇入 Gold 层 `fact_winter_event_zone_load`。

**评分公式（初版，权重待标定）**：

```
Winter Operational Load Score (0–100)
  = 0.35 × 加权服务请求量因子     (BO-1)
  + 0.30 × 作业缺口因子           (BO-2：是否被禁令/排班覆盖)
  + 0.20 × 天气严重度因子         (BO-3)
  + 0.15 × 应急事件因子           (WFPS 车祸相关出勤)
```

**归一化分母**：使用 `ngsx-caav` 路网算出各分区的街道公里数，
把绝对工单量转换为**单位路网负载**，避免大分区天然得分高。

**输出**：评分 + 负载等级（LOW / MED / HIGH / CRITICAL）+ 驱动因素归因 + 文字建议。

**验收标准**：19 个历史降雪事件全部能产出分区级评分，且评分与
实际投诉密度的相关性可解释。

### BO-7 · 纵向清雪状态数据集构建（数据资产，时间敏感）

> 把一个只有当前状态的公开数据集，变成可回溯的纵向数据集。

**数据依据【实测】**：`g3p4-h83y` Snow Clearing Status，237,867 行
（≈ 地址 × 街道侧），字段含 `has_street` / `has_alley` / `has_walk`
三个布尔型清雪状态——**但没有任何时间字段**，覆盖式更新，不保留历史。

**目标**：每日快照落 Bronze，构建此前不存在的地址级清雪状态时间序列。

**实现方式**（[ADR 0006](../adr/0006-storage-compute-query-stack.md) §2.2、§6）：

- 需新增 **`snapshot` 分区策略**——按**采集日**而非记录日期分区。现有四种策略都
  表达不了这个数据集：`daily` 强制要求 `timestamp_field`，而它没有任何时间字段；
  `static` 单一文件名会次日覆盖前一日。
- **以存储节点上的独立定时任务运行，不作为 Airflow DAG。** 这是全项目唯一
  "漏一天则永久丢一天"的任务，不应依赖可重建组件的可用性。代价是不受 Airflow
  重试与告警覆盖，需自带失败通知。
- **必须流式写入**：23.8 万行全量物化为 Python 对象会 OOM。分页拉取、边写临时
  gzip 文件、再分片上传，使内存占用只与单页大小成正比。

**论文价值**：可作为明确的贡献声明
（"we construct the first longitudinal record of address-level clearing status"）。

> 🚨 **优先级最高，且是唯一有时间成本的一项**——
> 数据只能从 DAG 上线当天开始攒。**每推迟一天，就永久少一天历史。**
> 建议在其他所有开发之前先上线这个采集 DAG。

## 2. 已知约束与风险（必须在设计中显式处理）

### 2.1 地理字段大面积缺失【实测】

| 范围 | 有 `neighbourhood` | 填充率 |
|---|---|---|
| 全表 18,346,621 | 3,832,509 | **20.9%** |
| 冬季相关 275,243 | 220,580 | **80.1%** |

**原因**：占 60.8% 的 Information Request 是电话咨询，无地址；只有真实派单才带位置。

**处理要求**：

- 所有空间分析的**有效分母是 383 万而非 1,835 万**，文档与图表必须标注清楚
- Silver 层必须输出 `has_geo` 标记列，Gold 层按该列过滤
- ⚠️ **与现有约定冲突**：CLAUDE.md 的「Escalate to human when」规定
  空间连接 NULL > 10% 需上报。本数据集全表 79% 无地理信息是
  **上游固有特性而非管道缺陷**，告警阈值需按「有地理信息的子集」计算，
  否则会持续误报。

### 2.2 渠道分类体系断层【实测】

`Self Service` / `Mobile` / `SMS In` 三个渠道在 2022 年后归零，
同期 `VOF` 从 3,910 暴涨至 91,202（23 倍）。判定为**记录口径迁移**而非行为变化。

| 影响面 | 结论 |
|---|---|
| 2022 前后**渠道结构**对比 | ❌ 不可直接比较 |
| **总量与类型**分析 | ✅ 仍可比 |
| Silver 层 | ⚠️ 必须建立渠道归一化映射（`Self Service + Mobile + SMS In → VOF`） |

### 2.3 供给侧样本量小

19 个犁雪事件 / 49 个禁令。**这不是缺陷，是业务现实**——
住宅区全市犁雪本就是低频重大操作。设计上通过展开到分区维度
（19 × 22 ≈ 400 观测单元）与社区维度来获得足够的分析样本。

### 2.4 工单总量长期下降

2013 年峰值 1,618,563 → 2021 年谷底 556,156（−66%），近年回升至 777,829。
已核实**是全局现象，非除雪类目被重分类**，故跨年比较在类型维度上仍成立，
但绝对量的年际比较需说明这一背景。

## 3. 分析设计：事件驱动而非投诉驱动

因 §2.3 的供给侧稀疏性，分析单元**不是「单条投诉」而是「降雪事件 × 分区」**：

```
Open-Meteo 降雪量(cm)  →  是否/何时发布禁令  →  排班执行         →  投诉响应
   驱动变量                 决策变量             供给变量            结果变量
  (日粒度, 18年)         (mfzv-893p, 49)    (tix9-r5tc, 418)   (311, 22万带地理)
```

**观测单元数**：49 事件 × 22 分区 ≈ 1,000，展开到 242 个 neighbourhood 后更多。
这是标准的 **event study** 设计。

**关键性质**：该设计**不依赖投诉量大**。投诉仅用于度量「市民感知的服务缺口」，
而非主要预测变量——这正面回应了「除雪投诉只占 311 的 1.5%」的质疑。

## 4. 实现方式与可行性评估

### 4.1 按分析类型划分

| 目标 | 分析类型 | 实现方式 | 可行性 |
|---|---|---|---|
| BO-1 需求侧负载 | **描述性** | SQL 聚合 + 滚动中位数阈值 | ✅ 数据已验证 |
| BO-2 供给侧执行 | **描述性** | SQL 聚合，事件级 | ✅ 数据已验证 |
| BO-3 降雪驱动 | **诊断性** | SQL JOIN + 剂量反应曲线 | ✅ 数据已验证 |
| BO-4 空间对齐 | **工程能力** | `ST_CONTAINS` 空间 JOIN | ✅ 边界数据存在 |
| BO-5 SLA 审计 | **规则评分** | 类型字典解析 + 时长计算 | 🟡 依赖 `closed_date` 语义确认 |
| BO-6 负载评分 | **规则评分** | 加权公式 SQL，完全确定性 | ✅ 依赖 BO-1~4 |
| BO-7 纵向数据集 | **数据采集** | 每日快照定时任务 | ✅ 但**时间敏感** |

**全部 BO 均为规则驱动，不含 ML 模型。** 项目重点是数据工程。

SQL 一律按 **Trino 方言**书写（[ADR 0006](../adr/0006-storage-compute-query-stack.md) §3）。
BO-4 的空间连接用 Trino geospatial 函数 `ST_Contains` / `ST_GeomFromText`，
输入是 Silver 层落的 WKT 字符串。

### 4.2 能力边界

| 场景 | 当前设计能否支撑 |
|---|---|
| 上次降雪哪个分区投诉最多 | ✅ |
| 各选区的 SLA 达成率排名 | ✅（BO-5） |
| 降雪 10 cm 大约会产生多少投诉 | ✅（BO-3 剂量反应） |
| 明天预报暴雪，应优先调配哪些分区 | ✅（规则 + 预报） |
| 我家这条街清了没 | ❌ **明确不做**，官方 app 已提供 |
| 实时作业车辆位置 | ❌ 无 GPS 数据源 |
| 预测下个冬季的总投诉量 | ❌ 需 ML，超出 MVP |

## 5. 非目标（明确排除）
