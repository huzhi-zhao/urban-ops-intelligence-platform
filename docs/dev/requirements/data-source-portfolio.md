# 数据源采纳台账

> 本篇回答的是**「哪些源我们用、哪些源我们暂时不用、将来要用时得先付什么」**。
>
> 它与 [winnipeg-data-sources.md](winnipeg-data-sources.md) 的分工是硬的，不要混写：
>
> | | winnipeg-data-sources.md | 本篇 |
> |---|---|---|
> | 回答 | 门户上**有什么**、实测规模与缺陷 | 我们**采纳什么**、为什么、启用要付什么 |
> | 性质 | 证据 | 决策 + 启用手册 |
> | 变更触发 | 上游数据集变了 | 采纳分级变了 |
>
> 常青文档，原地改写。**每个条目的分级只能按 §2 的判据改，且必须同时补上改级理由。**

---

## 0. 为什么需要这篇

到 2026-08-07 为止，数据源的信息散在四处：`winnipeg-data-sources.md` 的调研清单、
`business-objectives.md` 各 BO 的「数据依据」、`project-overview.md` 的数据源表、
`guide/data-sources.md` 的对外登记。四处都对，但**没有任何一处回答
「H2 要用 WFPS 出勤数据，我得先做什么」**——每次想启用一个源，都要把调研重做一遍。

更实际的驱动是 H2 的定义（[project-overview.md](project-overview.md) 「交付视野 · H2」）：
判据是**陌生团队能否接手**。一份只列了 H1 在用源的清单，交接时等于把「还有哪些
可以接、接了要花多久」这个判断整个丢掉。

所以本篇对 **H2 预备源的记录密度，刻意做得和 H1 在用源一样高**。
这是它最主要的价值——H1 的部分只是顺带。

## 1. 台账登记模板

每个条目按同一组字段登记。**字段缺失比字段为空更糟**：写「未测」也是信息，
留白会被下一个人当成「测过且没问题」。

| 字段 | 含义 | 缺失时写 |
|---|---|---|
| **ID / 端点** | Socrata dataset id，或外部 API 的完整入口 | —— |
| **认证 / 限流** | 是否要 key、速率上限 | `无` / `未测` |
| **规模 / 覆盖** | 行数与时间跨度，标注【实测】还是【元数据】 | `未测` |
| **解除什么约束** | 一句话：不接它，哪个分析做不了 | 不能留白，留白说明不该收录 |
| **分区策略** | 建议的 `partition_strategy` 与 `timestamp_field` | `待定` |
| **接入成本** | 要不要新 client / 新 fetcher / 新契约；能否复用现有通路 | —— |
| **启用前必答** | 启用之前必须先跑的探针（见 §6） | —— |
| **分级** | §2 的四级之一 | —— |

## 2. 四级分级与判据

| 级别 | 含义 | 判据 |
|---|---|---|
| **H1 在用** | 已进 H1 证据链 | 会议交付的五张图 / 八个 BO 里有一处**直接依赖**它 |
| **H1 条件触发** | 备着，某个探针的结果决定要不要接 | 触发条件必须写成**可判定的一句话**，不能写「视情况」 |
| **H2 预备** | H1 不接，H2 大概率接 | 它解除的约束是**运维 / 可交接 / 结论稳健性**层面的，不是 H1 讲故事的必需 |
| **不采纳** | 明确排除，附理由 | 防止半年后重新捡起来再论证一遍 |

> ⚠️ **分级不是优先级，是承诺。** 一个源进「H1 在用」，意味着它的失败会让 H1 交付
> 缺一块；进「H2 预备」意味着 H1 不为它花任何时间，包括不写契约、不写 YAML。

### 2.1 一条否决性判据：历史深度

**没有历史的源，不能进任何回溯分析。** 本项目的证据链全部是十年尺度的回溯，
一个只有滚动窗口（如 `bh78-7qpb` 的 2 个月）或只有当前状态（如 `g3p4-h83y`）的源，
无论字段多好，**在 H1 都只能做演示，不能做证据**。

这条判据看着显然，但它是 BO-7 整个设计的来源，也是 §5 里两个源被降级的唯一原因。
先问历史深度，再看字段。

## 3. H1 在用

### 3.1 需求侧 · 311 Requests

| | |
|---|---|
| ID / 端点 | `u7f6-5326` · `https://data.winnipeg.ca/resource/u7f6-5326.json` |
| 认证 / 限流 | `SOCRATA_APP_TOKEN`（可选，提高限额；回填必须带） |
| 规模 / 覆盖 | **18,346,621 行**【实测】，2008-06-17 → 至今 |
| 解除什么约束 | 唯一的需求侧信号。BO-1 / BO-5 的事实表 |
| 分区策略 | `daily`，`timestamp_field: open_date` |
| 接入成本 | 已接入（`SRC-WPG-311`） |
| 分级 | **H1 在用** |

缺陷全部记在 [winnipeg-data-sources.md §3](winnipeg-data-sources.md)，此处不复述。
本篇只补一条采纳层面的判断：**它是代理变量，不是观测值。**
投诉密度是「报告倾向」的函数——懂流程的社区投诉多，老年人多、新移民多、
英语不好的社区同样烂路投诉少（civic tech 的经典偏差）。因此它在证据链里的位置是
**提问，不是回答**，这也是 §4.1 收录 StatCan 的直接原因。

### 3.2 供给侧 · 排班 / 禁令 / 分区边界

| 数据集 | ID | 规模【实测】 | 在 H1 的角色 |
|---|---|---|---|
| Plow Zone Schedule | `tix9-r5tc` | 418 行 / 19 事件 × 22 分区 | **排班顺位**（`shift_number`）—— 供给侧唯一口径 |
| Snow Parking Bans | `mfzv-893p` | 49 行 | 决策事件日历；BO-3 的「决策滞后」 |
| Plow Zones | `39ur-higg` | 82 个 MultiPolygon / 25 个分区取值 | 空间归属，BO-4 交叉映射表的输入 |

三者均 `partition_strategy: static`，已接入。

> 🔴 `tix9-r5tc` 的口径在 2026-08-07 被推翻过一次：它是**排班计划表**，不是执行记录，
> `shift_end` 不能读作完成时间。决策与实测见
> [ADR 0008](../adr/0008-plow-schedule-is-a-plan-not-a-record.md)。
>
> **这次事故是本篇存在的另一半原因。** 立项期对这个源验的是「有没有、多少行、
> 字段在不在」，三条全对，结论仍然错——因为没人看过取值的**分布**。
> 分级判据因此明确要求「解除什么约束」必须写成一句可证伪的话，而不是「作为供给侧数据」。

### 3.3 驱动侧 · Open-Meteo

| | |
|---|---|
| 端点 | Archive API + Forecast API，REST 无认证 |
| 认证 / 限流 | 免费额度 <10,000 请求/日；一个窗口一次宽调用，不要按日循环 |
| 规模 / 覆盖 | 日粒度，历史任意长【实测通过】 |
| 解除什么约束 | 降雪事件切分（BO-3）的唯一输入；M1 的前瞻输入 |
| 分区策略 | archive → `daily`；forecast → `snapshot` |
| 接入成本 | 已接入（`SRC-Open-Meteo`，两个 dataset） |
| 分级 | **H1 在用** |

🆕 **本次新增的用法：按分区质心多点取数。**

当前只取单点 `49.895, -97.138` 代表全市。这在**空间上是常数**，因此
「排班顺位差异是不是因为那些区雪本来就下得多」这个必然会被问到的问题，
现有数据**答不了**。多点取数不是新源、不需要新 client、不需要新契约——
只是同一个 client 换一组坐标（22 个分区质心，或 15 个 ward 质心），
成本接近零，却把一个反证缺口直接补上。

> 代价要说清楚：Open-Meteo 的历史存档是再分析格点数据，市域尺度上分区之间的
> 降雪差异可能小于格点分辨率。**这本身就是探针的结论之一**——若多点之间无差异，
> 那结论是「降雪量不能解释顺位差异」，同样有用，且比不测强。

### 3.4 归一化分母 · 地址级清雪状态

| | |
|---|---|
| ID | `g3p4-h83y` |
| 规模 / 覆盖 | **237,867 行**【实测】，**无任何时间字段**，覆盖式更新 |
| 解除什么约束 | ① 分区地址数 = BO-6 的归一化分母；② 排班顺位的第一个反证变量 |
| 分区策略 | `snapshot`（唯一合法选择） |
| 接入成本 | 已接入（`SRC-WPG-SNOW`），2026-08-02 起每日采集 |
| 分级 | **H1 在用（一次快照）+ H2 主力（纵向序列）** |

**它在 H1 与 H2 是两个不同的源，必须分开理解**：

- **H1 只用当期一次全量快照**求分区地址数。求分母不需要历史。
  [ADR 0008 §4.3](../adr/0008-plow-schedule-is-a-plan-not-a-record.md) 的交叉验证已用它跑完：
  空间命中率 100.0%，`r(平均顺位, 地址数) = +0.491`。
- **H2 才用纵向序列**。它是全项目**唯一能突破「供给侧只有 19 个事件」这个天花板**
  的东西，而这个赌注已经下完、成本为零。检验点是 12 月（见 §7）。

### 3.5 🆕 社会经济基线 · StatCan 普查（Dissemination Area）

| | |
|---|---|
| 端点 | Statistics Canada Census Profile / 普查地理边界文件（DA 级）。非 Socrata，非门户 |
| 认证 / 限流 | 无认证；一次性下载，不是 API 轮询 |
| 规模 / 覆盖 | 聚合表，Winnipeg CMA 约数千个 DA；普查年（2021 / 2016 / 2011） |
| 解除什么约束 | **同时解除两个**：① §3.1 的报告倾向偏差校正；② 排班顺位的社会经济反证 |
| 分区策略 | `static` |
| 接入成本 | 中低。不走 Socrata client；DA 边界需 GeoJSON→WKT 通路（BO-4 已有同一条通路） |
| 启用前必答 | DA 边界与 plow zone / ward 的空间对齐命中率；普查年与分析窗口（2015–2026）的时间错配如何声明 |
| 分级 | **H1 在用** |

**为什么它是本次唯一新收的 H1 源。**

现在的叙事有一个结构性弱点：投诉密度既是需求侧的核心指标，又被自己承认是有偏的
代理变量（§3.1）。没有外部基线，这个弱点只能靠免责声明处理——
而免责声明改变不了结论强度。

DA 级的人口 / 年龄 / 语言 / 收入把两件事同时变成**可测的量**：

1. 「投诉少 = 服务好」还是「投诉少 = 不发声」——可以看投诉量对降雪量的**残差**
   与社会经济变量的关系。残差为负的社区，可能才是被忽视的地方。
2. 「排班顺位差异是否与社会经济分布相关」——这是把叙事从「理性地骂」
   升级为「可复核的研究」的关键一步。

> ⚠️ **表述纪律同样适用**（[ADR 0008 §4.2](../adr/0008-plow-schedule-is-a-plan-not-a-record.md)）：
> 相关不等于因果，顺位差异可能有完全正当的运营理由。本源的作用是让这个问题
> **可以被讨论**，不是替市政下结论。收录它的同时收录这条纪律。

## 4. H2 预备

> 本节的记录密度是**刻意的**。H2 的判据是「陌生团队能接手」，
> 而接手的第一个动作就是判断「还有哪些源可以接」。
> 每条都写到**启用当天可以直接开工**的程度。

### 4.1 `yg42-q284` · WFPS 消防与救护出勤

| | |
|---|---|
| 规模 / 覆盖 | **1,323,967 行**【元数据】，2014-12-31 → 至今，近实时更新 |
| 字段 | Incident Number · Incident Type · Call Time · **Closed Time** · **Motor Vehicle Incident (YES/NO)** · Units · Neighbourhood · Ward |
| 解除什么约束 | **结果侧的第二个变量，且没有报告倾向偏差。** 降雪 → 车祸 / 救护响应时长，是比投诉硬得多的结果度量 |
| 分区策略 | `daily`，`timestamp_field` 取 Call Time（字段真名未实测） |
| 接入成本 | **低**——普通 Socrata 表，走现有窗口式 fetcher，一份 YAML + 一个 backfill 脚本 + 一份契约。自带 Neighbourhood / Ward 文本字段，**不需要空间连接** |
| 启用前必答 | ① Call Time / Closed Time 的真实字段名与填充率；② 响应时长的分布（有没有 §3.2 那种「方差为零」的陷阱）；③ Ward 取值与 311 的 ward 是否同一套写法 |
| 为什么 H1 不接 | 它是**增强**不是必需——H1 的证据链在 §3 已经闭合。开一条新摄取路径 + 一次口径对齐，在四周窗口里性价比最低 |
| 触发条件 | 若 §3.5 的社会经济反证做完后仍需要一个**客观**结果变量，它是第一顺位 |

> 历史注记：它曾是 BO-6 评分的「应急事件项」（0.15 权重），因未实测被删除，
> 权重并入其余项。**恢复它需要重新论证权重，不是把 0.15 加回去。**

|---|---|

### 4.3 Winnipeg Transit Open Data API（GTFS）

| | |
|---|---|
| 端点 | `https://api.winnipegtransit.com/<path>`，路径加 `.json` 返回 JSON（默认 XML） |
| 认证 / 限流 | **需注册 API key**；**每 key 每 IP 每分钟 100 次** |
| 规模 / 覆盖 | 静态时刻表单文件下载、每日更新、遵循 **GTFS**；另有实时车辆位置 |
| 解除什么约束 | 冬季公交延误 = 又一个客观结果变量；GTFS 是国际规范，讲「可迁移性」时可直接引用 |
| 分区策略 | 静态 GTFS → `static`（或按发布日 `snapshot`）；实时 → `snapshot` |
| 接入成本 | **中高**——门户之外的第二套 API，要新 client、新认证、退避策略。**不是零成本复用** |
| 启用前必答 | ① key 申请周期；② 100 req/min 下拉一次全量要多久；③ 历史时刻表是否可回溯（多半不可，同 §2.1） |
| 附带价值 | 限流 100 req/min 是**真实的工程约束**，可以写进「速率限制与退避策略」章节 |

## 6. 收录前必须跑的探针

任何源进入「H1 在用」之前，五问全部要有答案。判据是**每一问都能用一条查询、
在几分钟内出一个数字**；出不来的那一问，就是这个源的真实风险所在。

| # | 问题 | 失败的样子 |
|---|---|---|
| 1 | **溯源语义**：这个字段记的是计划还是执行？谁在什么时刻写入？ | 口径整个作废（`tix9-r5tc.shift_end`） |
| 2 | **变异度**：指标在报告单元上的分布、方差、恒定值比例？ | 方差为零 = 指标不存在（同班次 `shift_end` 完全相同） |
| 3 | **对齐**：键连接完整率？原生粒度等于报告粒度吗？要不要分配？ | 静默 NULL 传播（22 vs 25 个 `plow_zone`） |
| 4 | **样本量**：分析单元数 × 每单元观测数，够不够跟基线比？ | 做不出显著性（19 事件） |
| 5 | **反证**：什么替代解释能推翻它？手上有没有数据排除？ | 结论被一句话打回（顺位 vs 地址数 / 路网 / 降雪） |

第 2 问与第 5 问是 2026-08-07 之前**完全缺席**的两问，也是最便宜的两问。
逐指标的探针结果落在 `metric-feasibility-audit.md`（另行执行），
本篇只登记源级的分级与启用成本，不重复记录指标级结论。

> 📌 **第 5 问是本篇与找新源之间的连接点。** 反证变量往往不在已采纳的源里——
> §3.5（社会经济）、§3.6（路网）两条都是第 5 问直接问出来的。
> **找新源的正确驱动力是「我要排除什么替代解释」，不是「还有什么数据有意思」。**
