# 项目概述

## 项目定位

**Urban Operations Intelligence Platform (UOIP)** —— 一个商业场景驱动的城市运营
数据平台。

模拟城市运营团队（311 调度中心、交通管理部门、应急响应调度组）的数据团队，
整合政府公开 API 与气象数据，评估未来 24 小时各行政区/社区的运营负荷水平，
并为公共资源（急救、市政维修、客服座席等）配置提供决策建议。

项目主体是**数据工程**，其上叠一层预测模型：

- Lakehouse 分层架构
- Spark ETL
- 数据仓库建模（星型模型 + 空间分析）
- Airflow 编排与增量摄取
- 预测层（需求预测 / 超时风险）驱动的运营决策支持系统

模型是管道之上的一层，不是它的替代——评分与推荐的骨架仍是确定性的，
模型为其提供前瞻输入并驱动排序。清单与评估协议见
[business-objectives.md](business-objectives.md) §4。

**部署城市为 Winnipeg (MB)，且只有 Winnipeg。** 数据源实测结果见
[winnipeg-data-sources.md](winnipeg-data-sources.md)。

## 交付视野

项目有三个视野。它们不是三个阶段——**H1 与 H2 是同一件作品的两次收敛**，
H3 只是一条不越过的线。区别在于「完成」由谁判定：

| | 视野 | 期限 | "完成"的判据 | 判定权在谁 |
|---|---|---|---|---|
| **H1** | 会议交付 | **2026-09-19** | 摘要的每一句都有真实数据支撑，且能现场讲清楚 | 摘要本身（[business-objectives.md](business-objectives.md) §0.2） |
| **H2** | 企业级 Winnipeg 城市智能服务 | **约 2026 年底** | 一个陌生团队能 fork 下来跑通并接手运维 | 一个不认识本项目的人，只读 [`guide/`](../../guide/) 能否独立完成部署与排障 |
| **H3** | 移植到其他城市 | 无期限，**多半不做** | —— | 只留围栏，不留实现 |

### H1 · 会议交付（当前唯一在跑的视野）

**Day of Data Winnipeg 2026，会期 2026-09-19**（Prairie Dev Con 已回复
speaker/session 已满、转介此会，见 [business-objectives.md](business-objectives.md) §0.2）。
**截至 9 月底，全部工作只服务这一个视野。**

判据是"**能讲**"，不是"能运维"。这条判据的作用是**授权推迟**：凡是只为长期
运维而做的工作（查询层、BI、CI/CD、可观测性、集成测试、契约冻结、手册完整度）
在 H1 一律不做，推到 H2。反过来，摘要点名的每一环都必须真实跑通——
**不接受"架构上支持"这种说法**，回测结果要能出现在幻灯片上。

交付分级（P0 / P0.5 / P1）与逐条对应的摘要义务见
[business-objectives.md](business-objectives.md) §0.3。

> ⚠️ 摘要至今**未被会方接受，也尚未正式投稿**（§0.2）。这不改变 H1 的期限：
> 期限的作用是约束范围，而不是等待外部确认。

### H2 · 企业级 Winnipeg 城市智能服务（最终交付，一定会做）

H1 交付的是一次可信的回测；H2 把它变成**一套可以被别人接手的城市智能服务**。
目标读者从"听众"变成"运维者"——设想 Winnipeg 市政或同类机构想基于公共数据
自建这样一套服务，**可以直接复用本项目**，而不是把它当参考实现重写一遍。

判据一句话就能验：**陌生团队照 `guide/` 能否独立跑起来并接手运维。**
这句话把 H2 的工作内容完全确定下来，不需要再列愿望清单：

| 判据落到哪 | 具体内容 |
|---|---|
| 跑得起来 | 一条命令拉起全栈；MinIO / Spark / Airflow 环境实测通过（当前 S3 代码只跑过 mock 单测） |
| 查得到 | Hive Metastore + Trino + Superset —— H1 可以用 Spark 直读 Parquet 绕过，H2 不能 |
| 信得过 | 数据契约冻结、数据质量框架落地、行数与命中率基线告警、集成测试跑真 MinIO |
| 出了事能修 | 可观测性、runbook、失败路径的处置手册 |
| 改得动 | CI/CD 门禁、DAG 自动部署、数据字典 |

**H2 不是 H1 的超集重做。** H1 的产物（Bronze / Silver / Gold / 模型）原地保留，
H2 补的是它们外面的一圈：查询、运维、质量、交接。

### H3 · 向其他城市移植（留围栏，不留实现）

平台叫 UOIP 而不叫 WOIP，城市是配置维度——这个设计保留。
但要明确：**H3 几乎肯定不会被执行**，NYC 或任何第二个城市都不在计划内。

因此 H3 的**成本上界是零**：

- ✅ 留围栏——`CLAUDE.md` 的三条城市无关护栏 + CI 的 grep 门禁。
  它们的边际成本已经付过了，继续遵守不花钱。
- 🚫 不留实现——不建多城运行时、不在存储路径里加 `city` 维度、
  不为"第二个城市"预留抽象层、不维护第二个城市的存量代码。

**围栏不等于实现。** 判断某项工作属于哪边，用一个问题：
*不移植城市的话，这件事还值不值得做？* 值得（比如"业务语义进配置不进代码"
本身就让代码更可测），那就做；不值得（比如"抽象一层 CityAdapter"），那就不做。

> **推论：NYC 存量退役。** 此前的定位是"NYC 是可移植性的实证基线"——
> 该论证依赖 H3 有真实价值。H3 降级为围栏之后，这个论证不再成立，而维护一份
> 半迁移状态的第二城市代码是持续成本：13 个 DAG 里 10 个属于 NYC、
> `spark/jobs/` 两个 Silver 作业一个是 NYC borough 边界。
> 更实际的是它与 H2 的判据直接冲突——**一个号称可复用的 Winnipeg 平台，
> 不能内含半个别的城市。**
>
> 可移植性此后由**围栏 + CI 门禁**保证，不由第二份实现保证。
> 唯一例外：`SRC-Open-Meteo` 与 `SRC-DCP` 的 GeoJSON→WKT 通路是 Winnipeg 也需要的
> **能力**，它们按角色名泛化后保留，不随 NYC 删除——退役的是城市实例，不是能力。

## Winnipeg 相对既有实现的新工程前提

既有实现基于 NYC 开放数据构建，Winnipeg 并非只是换一份配置：

| | 既有实现（NYC，退役中） | Winnipeg |
|---|---|---|
| 行政粒度 | 5 个 Borough | **15 个 ward + 242 个 neighbourhood** |
| 作业粒度 | 与行政区一致 | **22 个 plow zone，与行政区不嵌套** |
| 几何套数 | 1 套 | **3 套互不嵌套** |
| 供给侧数据 | 无 | **有**（排班 + 禁令），因而可做问责性分析 |
| 核心运营议题 | 全年综合负载 | **冬季除雪**（"Winterpeg"） |

「作业几何 ≠ 行政几何」是全项目最硬的工程前提，也是既有实现完全没有遇到过的
问题，见 [business-objectives.md](business-objectives.md) BO-4。

> 两地门户同为 Socrata 平台，**摄取层可零改动复用**——这是既有实现留给
> Winnipeg 的真实资产，也是它退役后仍然值得的原因。

## 商业背景

城市服务与作业资源有限，调度部门在每次降雪事件中需要回答三个问题：

1. 哪些社区/作业分区在本次事件中**服务负荷最高**？
2. 负荷高的**原因**是什么——降雪量大，还是该分区在排班中一贯靠后？
3. 下一次降雪应如何**在住宅区优先级内部调整分区作业次序与资源投放**？

> ⚠️ 第 2 问原为「作业未覆盖」，第 3 问原为跨优先级的调度建议。两处都已收窄：
> 排班表证明不存在未覆盖的分区（ADR 0008），而跨优先级次序是政策规定的，
> 不接受数据挑战。见 [business-objectives.md](business-objectives.md) §3.1 与 BO-8。

现状是需求侧（311 投诉）、供给侧（犁雪排班/禁令）、驱动侧（气象）三类数据
分散在不同端点，且**使用三套互不对齐的地理口径**，缺少统一平台与自动化评估机制。

痛点有硬证据：CBC 报道 2023 年除雪超预算 **420 万加元**，
除雪议题每年都是市议会与本地新闻的固定项。

## 需求范围（MVP = H1）

聚焦**冬季运营**：

```
Winter Operational Load Score (0–100)
  = 0.40 × 预测服务请求量因子（M1 输出）
  + 0.30 × 排班顺位因子（该分区被排在第几批）
  + 0.30 × 天气严重度因子
```

绝对量按**分区地址数**归一化，避免大分区天然得分高。

输出三项：分区运营负荷排名、负荷原因归因、资源配置建议。
排名由预测值驱动，评分与归因的骨架是确定性的。

> 🔴 **第二项于 2026-08-07 换过**：原为「作业缺口因子（降雪事件是否被排班覆盖）」，
> 实测证明该量恒为假（19 次事件全部 22/22 全覆盖），且排班表只记全市集中犁雪、
> 沉默不构成未出动的证据。决策见
> [ADR 0008](../adr/0008-plow-schedule-is-a-plan-not-a-record.md)。

MVP 的必做模型是**需求预测 M1**——它是对外标题 "AI-Driven" 的落点，
也是评分能够前瞻而非仅回顾的前提。超时风险 M2 为 P1（摘要未要求），
SLA 合规性审计不在本轮范围内。交付分级见
[business-objectives.md](business-objectives.md) §0.3，理由见其 BO-5。

评分的**有效分析窗口为 2015-12 起**——供给侧排班数据的起始时间。
更早的冬季只用于 M1 训练，不产出评分（business-objectives BO-6）。

详细的业务目标拆解、验收标准与已知约束见 [business-objectives.md](business-objectives.md)。

## 数据仓库设计

星型模型：

- **事实表**：`fact_service_requests`（需求侧）、`fact_plow_shifts`（供给侧）、
  `fact_emergency_calls`、`fact_winter_event_zone_load`（事件×分区聚合，承载评分与建议）
- **维度表**：`dim_date`、`dim_time`、`dim_geography`、`dim_weather`、
  `dim_request_type`（3,563 个 `type` 取值的归一化字典，解析优先级与时段）、
  `dim_recommendation_rules`
- 事实表按日期分区，按作业分区（`plow_zone`）聚簇

> `dim_geography` 必须同时承载 **neighbourhood / ward / plow_zone** 三种归属，
> 因为三者互不嵌套（242 / 15 / 22）。这是与既有 NYC 实现（5 个 Borough 一套几何）
> 最大的建模差异，见 business-objectives BO-4。

## 设计原则

- 以真实生产系统为标准，不以学习演示为目标
- 优先采用企业级数据工程实践（分页处理、late-arriving facts、幂等性）
- 所有设计需同时解释业务价值与技术价值
- 考虑可扩展性、可维护性和成本控制
- 敏捷交付，逐阶段完成 MVP

**"企业级"在两个视野里是两个意思，不要混用**：

- **H1 的企业级**指*做法*——幂等、分区、契约、可重放，即使只跑过一次也按生产写。
- **H2 的企业级**指*可交接*——别人能跑起来、查得到、出了事能修。

H1 允许"跑过一次、结果可信、没有运维面"；H2 不允许。
先按 H1 的判据交付，不要在 9 月前用 H2 的判据自我加码——那是本项目最可能
错过期限的方式。
